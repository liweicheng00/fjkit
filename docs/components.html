Every macro, and the call that made it

Every macro, with a live preview and the call that produced it, grouped by the file it lives in and in the order src/fjkit/templates/ui/ lists them. Turn the knobs and two things change together: the component, and the Jinja you would have typed to get it. Every preview was rendered by fjkit's own Environment at build time.

01

Button

One element, seven variants, seven sizes — and no class at the call site.

Every parameter on this page is a closed enumeration. There is no class= escape hatch and no hue to pass: you pick a variant, and the token layer decides what it looks like. Anything a macro does not name becomes an HTML attribute, so hx_post="/tasks" renders as hx-post="/tasks". That conversion is one file, ui/attrs.html, which every macro forwards its leftover keywords to and no app ever calls. It is why htmx appears in no macro definition in the kit, and why a keyword a macro has never heard of is an attribute rather than an error.

button is the macro every other file reaches for, and the one whose signature is worth learning first: variant and size are closed lookups, href switches the element to an <a> and drops type, and icon_name takes any Lucide name so a caller never imports icon to put a glyph on a button.

button_group is two components under one name, and the knob tells you which: horizontal is a row, so the gap is yours; vertical is Basecoat's .button-group, which joins the buttons into a single control with shared borders and has no gap to give.

Data
The file that displays a value — a count, a state, a person, a definition.
      

      
      

        The largest file in ui/, and the one an ordinary page spends most of its calls
        on. The four with knobs are below; the rest follow, one rendered example each.
      

      

        empty_state is worth knowing before you need it. table renders it
        for you when rows is empty, so no caller writes the if-rows-else branch.
      

      

        avatar is the one whose signature to read. The name is both the alt
        text and the fallback initials, so the two cannot disagree, and the initials leave the
        accessibility tree the moment an image carries the name. Otherwise the same person is
        announced twice, once properly and once as two stray letters.

      03


      


Disclosure
Two disclosures, and not one line of fjkit JavaScript between them.
      

      
      

        collapsible is a native <details>: the open state, the
        keyboard operation and the disclosure role all come from the element, and Basecoat animates
        it with CSS. tooltip is drawn entirely from a data-tooltip
        attribute — no second element exists.
      

      

        The tooltip's mechanism has one consequence: CSS content() is never in the
        accessibility tree. A tooltip is a hint, never the only label a control has. Give the control
        an aria_label when the tooltip is the only text on it.
      



    
    

      


accordion(multiple) / collapsible(summary, open) — both take a block
      

    
      
    




  
        

  


  

    
    

      


tooltip(text, side, align) — the block is the element it wraps

Feedback
Five ways of saying "wait", "done" and "that did not work".
      

      
      

        These differ in who is waiting and for what, which is how you pick one. alert is
        a fact that stays on the page. spinner and skeleton both mean "not
        yet", and the choice between them is whether you know the shape of what is coming: a skeleton
        draws that shape, a spinner admits you cannot. dialog interrupts.
        toast outlives the response that raised it.
      

      

        Two of them make an accessibility decision for you.
        alert(variant="destructive") takes role="alert", which interrupts a
        screen reader mid-sentence; every other variant is role="status", which waits for
        a pause. A multi-line skeleton is one live region rather than six, because six
        bars are one thing loading.

      05


      


Form
Every field takes the same five parameters, and error replaces the hint.
      

      
      

        Every field macro takes the same name, label, hint,
        error and id, and error replaces the hint rather
        than stacking on it while marking the control aria-invalid. The playground
        walks five shapes of the same form: the htmx one, a field in error, the long controls, the
        radios-versus-select choice, and switches inside a fieldset.
      

      

        target= is what makes a form an htmx form; drop it and the same macro emits an
        ordinary POST that works without JavaScript.
      

      

        The two below are the fields that correct their own mechanism. range_field writes
        the filled part of the track for the first paint: Basecoat paints it from a custom property
        and updates it from JavaScript only on drag, so without that the bar sits at upstream's
        default and disagrees with the number beside it.

Icon
1,767 names, no sprite sheet, no icon font, no request.
      

      
      

        icon("plus") inlines the Lucide path as an <svg>. It
        inherits currentColor, so an icon inside a primary button is already the right
        colour, and it costs no network request at any size.
      

      

        Most macros take icon_name= directly — button, stat,
        empty_state, brand, sidebar_link — so you rarely call
        this one yourself. The links in this site's sidebar are all of them. A sample of the set is
        below, and any Lucide name works.
      




    

      


icon(name, size=16)
      

    
      
        




  


            

      

        An unknown name raises at render time rather than printing an empty box, so a typo fails the
        page that has it instead of shipping a hole in the interface.

Layout
The moment you type grid gap-4, the no-build promise is over.
      

      
      

        Components alone do not get you to a closed vocabulary. The first time you need two cards
        side by side you reach for a utility class, and the stylesheet fjkit shipped has no idea you
        wanted it. So spacing and columns are macros too. Every value is a lookup whose entries appear
        verbatim in the kit's source, where Tailwind can see them.
      

      

        The dashed tiles are your content. Change the knobs and the source line changes with them.
      

      

        The other three in this file are what a page is made of before any of its data arrives.
        page_header takes a block, and the block is its actions: a title, a description
        and a row of buttons stay on one line at every width, with no caller measuring anything. The
        header at the top of this page is the same macro with no actions to place.

Nav
The header's three pieces, and the trail that says where you are.
      

      
      

        These are the shell's header, split out so an app can import them without importing the
        template it extends. Two of the three are already on this page: the mark at the top of the
        rail is brand, and the switch in the header is theme_toggle.
      

      

        nav_links takes route names, not URLs, so the active state comes from comparing
        routes rather than string-matching paths, and stays correct when a URL gains a query string.
        Past about six destinations a header row runs out of width; fill the shell's
        sidebar block instead.
      

      

        breadcrumb takes (label, href) pairs, where a null href marks the
        current page. That is deliberate: the usual way this component goes wrong is a trail whose
        last entry links to the page you are already on, and the shape of the argument makes that
        unspellable.

Overlay
One id in, four out — and a mismatch fails without a word.
      

      
      

        Everything in ui/overlay.html is driven by Basecoat's own JavaScript, which the
        shell already loads and which re-scans on htmx:afterSwap, so an overlay that
        arrives in a swap works with nothing extra.
      

      

        What they share is id wiring. A trigger and its panel find each other through
        four related ids, and getting one wrong fails silently: the panel opens but is never
        announced, or never opens at all. Every macro here takes one id and derives the
        rest, which is why they are macros rather than markup to copy.
      

      

        select_menu and combobox put their value in a hidden input,
        pre-filled. Upstream ships value="" and writes it from JS, which loses the
        selection on any round trip that re-renders the fragment. Prefer select_field to
        either: a native <select> is correct for free and costs one element instead
        of thirty.
      

      

        Both take multiple=true, and both then want a list in selected where
        they took a scalar before. The hidden input carries Basecoat's JSON array, and
        multiselect_scripts() — one script, opted into by the page that has such a field
        — re-emits it on submit as the repeated field HTML has always used:
        labels=bug&labels=ui. The route stays ordinary at
        labels: list[str] = Form([]), with no parsing anywhere. Forget the script and the
        field posts one JSON-shaped string instead, which is a 422 on a page that looks correctly
        filled in.
      

      

        A checkbox group inside a fieldset posts the same thing and needs no script at
        all. It is the better answer up to about a dozen options, which is where these two start.

Shell
The one file you extend instead of importing — and the page you are reading.
      

      
      

        shell.html has no macros and no preview, because the preview is this page. It
        owns the <head>, the theme flash-guard, the asset links, the toaster and
        the header/main/footer skeleton. What it does not own — your brand, your navigation, your
        footer text — are blocks.
      

      

        One of them changes the shape of the page rather than its contents. Fill
        sidebar and the skeleton becomes a side column plus a thin top bar; the shell
        tests that block for emptiness itself and adds the sidebar_trigger to the
        header, so an app never sets a flag to say which layout it wanted.

Sidebar
A back office outgrows a header bar at about six destinations.
      

      
      

        The rail on the left of this page is this file. There is no preview in a card below: the
        panel is position: fixed, so a copy of it here would cover the page rather than
        sit in it. The running instance is on the left, and the call that produced it is printed
        below.
      

      

        Route names again, an icon by name, closed enumerations, and no class string anywhere in the
        signature. open is the desktop starting state only: on a narrow screen the
        sidebar always starts closed, because it renders as a full-screen overlay there and a page
        that opens covered by its own navigation is a bug rather than a preference.
      

      

        With JavaScript off, the server-rendered aria-hidden="false" leaves a wide
        screen fully navigable and hides the overlay on a narrow one. The links are in the HTML
        either way, so a crawler and reader mode still see them.

Table
Pass rows and the macro owns the empty case.
      

      
      

        columns is a list of dicts — label, and optionally
        align or width — and the macro tests rows to decide
        whether to render your body or the empty state. That is why it takes rows it does not
        iterate: no caller repeats the if-rows-else branch, and no page can ship a table that renders
        as a lone header row.
      

      

        A repeated row is a macro call inside your loop. {% include %}
        there is a template lookup plus a fresh context per iteration, which is the difference the
        benchmark on the Learn page measures.

Tabs
Two ids, passed once, and the keyboard is Basecoat's.
      

      
      

        Basecoat owns which tab is selected, the roving tabindex and the arrow keys, and the shell
        already loads it. This macro carries the aria contract that behaviour reads: a
        [role="tab"] whose aria-controls names a
        [role="tabpanel"] with that id. Getting that pairing right by hand is what a
        component should stop you having to think about.
      

      

        selected names the tab that starts open. The server knows which one the request
        was for, so it is a parameter rather than something a script decides after paint. The two
        representations under every playground on this page are one of these.
      



    
    

      


tabs(items, label, selected) / tab_panel(id) — both take a block
