Build the interface where you build the routes

Twelve lessons: how a fjkit app is wired, what htmx actually sends, how a rebrand works, and the command that fails a build. Every demo below is live.

This page is the thing it documents

Not a screenshot of it.

Every preview below is real macro output, rendered by fjkit's own Jinja environment at build time. So is the page around them. The sidebar, these cards, the tables and the tab strips are the same macros the demo app calls, and fjkit check runs over this site's templates in CI. Nothing here can show you a component the package does not ship.

01

Wiring: config, mount, render

Everything else you write is your app, not your front end.

A fjkit app touches the kit in exactly three places. FjkitConfig holds every knob. mount_fjkit() serves the stylesheet and the vendored JS straight out of the installed package, and builds the Jinja environment once per process. @render names the template a route answers with.

Click through the four files. There is no package.json and no watcher to keep running. examples/fjkit-demo in the repository is the same four files in a working app.

htmx

      


The htmx request and response
The server answers a swap with HTML. Nothing is serialised for it, and no client-side state is kept in sync.
      

      
      

        This is the whole idea, and it is smaller than it looks. An element says which
        request to make, and where to put the answer. The server answers with a piece of
        HTML, the same markup it would have put in the page. htmx drops that piece into the element
        you named.
      

      

        Nothing is serialised for the swap. Nothing is re-rendered on the client. No state lives in two
        places. The same route will happily answer a script in JSON — that is lesson 09
        — but that is a second door, not a step in this exchange. Press the button:
        the request below is real. htmx is loaded on this page, and a mock server in the
        browser plays the FastAPI side.
      




    

      


One round trip
The only thing that changes on the client is the subtree named by hx-target.

htmx

      


hx-target and hx-swap
Two attributes decide everything: which element, and how it is replaced.
      

      
      

        hx-target picks the element.
        hx-swap says what to do with it. This pair is
        where most htmx confusion lives, so try them against a live board. Every combination below runs a
        real request and swaps the real response.
      

      

        outerHTML replaces the target itself, so the response has to include the
        wrapper. innerHTML (the default) replaces what is inside it, so the response
        must not. Mixing those two up is the classic bug: you get a board inside a board.

htmx

      


Partials: one file, page and swap
The page embeds the fragment the htmx endpoint returns — so they cannot drift.
      

      
      

        Now the fjkit half. A partial is any template whose name starts with an underscore. It never
        extends the shell, it declares its own imports, and it wraps itself in the element the swap
        replaces. The full page {% include %}s it; every htmx
        endpoint returns it bare.
      

      

        That is why a fjkit app has no "update the row" code path. Every mutation re-renders the
        whole board partial and swaps it. One definition of what a board looks like, used by the
        first paint and by every request after it. The real files are
        examples/fjkit-demo/app/templates/tasks/ in the repository.

The board, live — add, advance, delete
Every control targets #demo-board, and every response is the whole board partial.

Traps worth knowing
      

    
      
    

      
full page back
returning page.html from an htmx route nests a whole document inside your div — return the partial
    
  
    

      
4xx does not swap
htmx ignores error responses by default. The shell adds 422, and only 422, which is what lets a rejected form come back as the form itself
    
  
    

      
lost wrapper
outerHTML needs the wrapper in the response, or the target disappears
    
  
    

      
stale filter
a row action must carry the active filter, or the swap silently resets the view
    
  
    

      
inherited swap
hx-target and hx-swap are inherited from ancestors. A button inside a card that polls itself with outerHTML inherits that swap, and replaces the element it meant to fill — spell both out on any trigger nested inside another htmx element
    
  

  

      
    

      


Server-side helpers
      

    
      
    

      
HX-Request
the header that tells a route it is answering a swap
    
  
    

      
HX-Trigger
response header that fires a client event — how fjkit raises a toast from a swap, which has no toaster in it
    
  
    

      
HX-Redirect
full-page redirect from inside a swap response
    
  
    

      
hx-swap-oob
one response, several regions — the next lesson
    
  

  











      06
htmx

      


One reply, many regions: hx-swap-oob
hx-target names one element. When one answer has to move six, the other five carry their own address.
      

      
      

        Every swap so far has had one target, and that is enough while the things that change sit
        under one element. The board is a single <div id="board">: every control on
        it points there, and every response is the whole board.
      

      

        A search result is not one thing. One query moves a row of counters above the table, the table
        itself, a progress card, a facet list and a siblings panel in the aside, and a detail panel
        below it — six fragments in three places, and the only element that contains all six is
        <body>. Swapping the body is a page reload with extra steps.
      

      

        So the reply carries the other five out of band — outside the one channel
        hx-target describes. Each of them says where it belongs by carrying the id it is
        going to.
      




    

      


What comes back from one keystroke
GET /search?q=cache, answered by one handler and one response model.
      

    
      
        
<div id="search-matches">…</div>                     ← no marker: this is what hx-target gets
<div id="search-stats"    hx-swap-oob="true">…</div>   ← flies to the counters
<div id="search-progress" hx-swap-oob="true">…</div>   ← flies to the aside
<div id="search-facets"   hx-swap-oob="true">…</div>   ← flies to the aside
<div id="search-related"  hx-swap-oob="true">…</div>   ← flies to the aside
<div id="search-detail"   hx-swap-oob="true">…</div>   ← flies below the table




  


      
    

      


What htmx does, in order
      

    
      
    

      
1 — lift
every top-level element carrying hx-swap-oob is lifted out of the response
    
  
    

      
2 — place
each one is matched to the element on the page with the same id and replaces it
    
  
    

      
3 — then the target
whatever is left is swapped into hx-target as usual
    
  

  


      
    

      


Four things to know
      

    
      
    

      
the value
true replaces the matching element; innerHTML, beforeend and the rest of the swap vocabulary all work here too
    
  
    

      
it fails in silence
an id that matches nothing is dropped without a word — no error, no console entry, and that region simply keeps the previous query's numbers
    
  
    

      
top level only
an out-of-band fragment nested inside a wrapper is not one — which is why the reply template is a flat list of includes
    
  
    

      
not the target
never mark the fragment that hx-target names: it would be lifted out too, and the target would be swapped with nothing
    
  

  




      

        On the fjkit side there is no new machinery. The page and the reply
{% include %} the same six partials and differ in one
        variable: the page renders them cold, the reply renders them addressed. Each partial defaults
        the flag itself, so it still renders standalone.
      




    

      


One set of partials, two ways of rendering them
      

    
      
        
{# _results.html — what an htmx request gets #}
{% include "search/_matches.html" %}
{% with oob = true %}
  {% include "search/_stats.html" %}
  {% include "search/_progress.html" %}
  {% include "search/_facets.html" %}
  {% include "search/_detail.html" %}
  {% include "search/_related.html" %}
{% endwith %}

{# _stats.html — and every other region, at the top #}
{% set oob = oob | default(false) %}
<div id="search-stats"{% if oob %} hx-swap-oob="true"{% endif %}>
  …
</div>




  


      

        The payoff is that where a fragment lives is decided by the page, once. Move the facet
        card from the aside into the main column and the router, the response model and the swap are
        all unchanged. The working files are
        examples/fjkit-demo/app/templates/search/ in the repository — and the next
        lesson is the other half of that same page, because a real screen needs both.
      











      07
htmx

      


One id, many fragments: HX-Trigger
The opposite problem to lesson 06: the trigger produces an id, and each region has a different question to ask with it.
      

      
      

        The last lesson worked because one handler could answer every region at once — one query, six
        fragments, one response model holding all of them. Opening a row on that same page is not that
        shape. What the click produces is an id, and the panels that care about it each
        need a different query: the detail of that task, the other tasks its owner has. A
        handler that answered all of them would have to import every service on the page, and adding a
        third panel would mean editing it.
      

      

        So the pick answers with its own region — the table, with the row now marked — and
        sends the id out in HX-Trigger. htmx raises that header as a DOM event, and the
        fragments that care listen for it and go and fetch their own data. The route does not know how
        many of them there are, or that any of them exist. Adding a panel is one more subscriber and no
        change to any route.
      




    

      


The route that picks
A GET, because picking changes nothing on the server. The table is the button's hx-target, so the reply swaps it in band.
      

    
      
        
@router.get("/search/select/{task_id}", name="search_select")
@render("search/_matches.html",
        hx_trigger=lambda task_id: {"task-selected": {"task_id": task_id}})
def select_task(service: ServiceDep, task_id: int, q: str = "") -> MatchesResponse:
    """Mark the row, answer with the table, and tell the panels which id."""
    return _matches(service, q, _selected(service, task_id).id)





  


      

        hx_trigger is where the event is declared, and it is a parameter of
        @render rather than a header the handler writes, for one reason: then it works
        the same on a route that does render. A callable is resolved per request out of the
        handler's own parameters by name — task_id here — plus result, what
        the handler returned. Returning None from it raises nothing, so a route can
        broadcast only sometimes.
      

      

        Nothing about that route is special otherwise. It is an ordinary partial route — one template,
        one response model — with an event attached, which is what makes the pattern cheap: the swap
        and the broadcast are one round trip, declared in one place.
      

      

        A second action on the same page shows the other half of it. Advance changes a status, so it
        raises a different event, and a different set of fragments cares.
      




    

      


A second event, from a route that changes something
The reply is the swap — the detail panel is this button's hx-target — and the header is what the other four hear.
      

    
      
        
@router.post("/search/advance/{task_id}", name="search_advance")
@render("search/_detail.html",
        hx_trigger=lambda task_id: {"task-changed": {"task_id": task_id}})
def advance_task(service: ServiceDep, task_id: int) -> DetailResponse:
    """Advance the task, answer with the detail panel, and say what changed."""
    if service.advance(task_id) is None:
        raise HTTPException(status_code=404, detail="task not found")
    return DetailResponse(selected=service.get(task_id))





  


      

        Two events, and each fragment picks the ones it has a reason to hear. The counters listen for
        task-changed and not task-selected, because picking a task changes no
        count. The facets listen for neither, because advancing one changes no owner and no priority.
        Which broadcasts a fragment hears is the fragment's own decision, and no route knows it
        exists.
      




    

      


Who hears what
      

    
      
      

      

        
          

              Fragment
              task-selected
              task-changed
              Why
          

        
                

          the results table
          no
          yes
          it is the pick reply's own target; an advance changes what a row says
        

        

          the detail panel
          yes
          no
          it is the advance reply's own target — hearing that event is the loop
        

        

          the siblings panel
          yes
          yes
          whose siblings these are, and what their status is
        

        

          the counters, the progress card
          no
          yes
          a pick changes no count; an advance does
        

        

          the facets
          no
          no
          no facet on that card is about a status
        


      

    




  


      

        One rule holds this together: the fragment a route answers with must not subscribe to
        the event that route raises. It is already being replaced in band, so hearing the
        event too fetches it a second time for the same click — and on a fragment that is its own
        target, it never stops. htmx will not save you, because a subscriber asking for its own URL is
        exactly what the attribute says to do. That is why the table hears only
        task-changed and the detail panel only task-selected: each is a
        route's target for one event and a subscriber for the other, never both for the same one.
      




    

      


The subscriber
These attributes on every region that cares, and nothing on the ones that do not.
      

    
      
        
{# a panel that needs only the id #}
<div id="search-detail"
     hx-get="/search/detail"
     hx-trigger="task-selected from:body"
     hx-vals="js:{task_id: event.detail.task_id}"
     hx-target="this" hx-swap="outerHTML">…</div>

{# a region that also depends on the search box #}
<div id="search-stats"
     hx-get="/search/stats"
     hx-trigger="task-changed from:body"
     hx-include="[name='q']"
     hx-target="this" hx-swap="outerHTML">…</div>




  


      
    

      


The attributes that matter
      

    
      
    

      
who is listening
from:body — htmx raises the event on the element that made the request, and it bubbles. The panels are nowhere near that element, so they listen where it arrives
    
  
    

      
how the id arrives
hx-vals="js:…" is the one place the id turns back into a query parameter. Reading it out of the event, rather than remembering the selection on the server, is what keeps the endpoints stateless and two open tabs independent
    
  
    

      
what else it needs
hx-include — for what the event does not carry. The counters are counts over the matches, so they need the search box as well as the id, and a selector fetches it off the page instead of every event having to carry it
    
  
    

      
what gets replaced
hx-target="this" — every subscriber replaces itself, so a reply is always one region and the sender never has to know how many regions exist
    
  

  


      
    

      


Four things to know
      

    
      
    

      
send an object
the trigger value must be a JSON object. htmx passes an object through as event.detail and wraps anything else — an array included — as {value: …}, so a listener reading event.detail.task_id finds nothing
    
  
    

      
it fires before the swap
HX-Trigger fires before the swap. That is exactly why the id travels in the event: a hidden input holding the selection would still hold the old one when the subscribers read it. HX-Trigger-After-Swap is the header for the other order
    
  
    

      
inheritance leaks in
hx-vals is inherited, and htmx merges it up the tree on a path that does not consult hx-disinherit. An htmx element inside a subscriber — the row's own title, which is the button that opens it — has to say hx-vals="unset", which is the only value that stops the walk
    
  
    

      
N panels, N requests
N subscribers is N requests. That is the trade: the page fans out instead of the handler fanning in, and hx-sync or a cache is where you pay it back if the queries are expensive
    
  

  




      

        The two lessons are not competing, and the demo does not put them on separate pages. They
        answer different questions, and /search asks both: a query is one question the
        server can answer completely, and a pick is an id that three regions each have a different
        question about.
      




    

      


Which one a page needs
      

    
      
      

      

        
          

              Ask
              hx-swap-oob
              HX-Trigger
          

        
                

          what produces the change
          one query the server can answer for every region
          an id each region has a different question about
        

        

          who knows the regions
          the handler — it renders all of them
          nobody; each region declares itself
        

        

          requests per interaction
          1
          1 + one per subscriber
        

        

          adding a region
          edit the handler, the model and the reply template
          one more subscriber; nothing else changes
        


      

    




  


      

        The working files are examples/fjkit-demo/app/features/search/ and
        app/templates/search/ — the same page as the last lesson. Every region there
        carries a render stamp, so which ones each action reached is readable on the page itself,
        without opening the network tab. A query is one request and six new stamps. A pick is three
        requests and three stamps — the table, the detail panel, the siblings panel — while the
        counters, the progress card and the facets sit still. An advance is five, and this time the
        facets are the only card that does not move.
      











      08
htmx

      


While the request is in flight
A swap is a round trip, and nothing stops a second click during it. Two attributes cover the whole of the wait.
      

      
      

        htmx adds the class htmx-request to an element for the length of a request and
        removes it afterwards. Without hx-indicator that element is the one that fired the
        request; with it, it is whatever the selector names. Then this stylesheet — htmx's own, injected
        at startup — does the rest:
      




    

      


The rules htmx injects
Two selectors, comma separated.
      

    
      
        
.htmx-indicator { opacity: 0; visibility: hidden }

.htmx-request .htmx-indicator,
.htmx-request.htmx-indicator { opacity: 1; visibility: visible; transition: opacity 200ms ease-in }




  


      

        The first selector covers an indicator inside the marked element — a spinner in the
        button that was clicked. The second covers an indicator that is the marked element,
        which is the shape fjkit uses: spinner(indicator=true) adds
        htmx-indicator and nothing else, so a loading state costs no CSS and no JavaScript
        of yours, and no round trip to reveal it.
      




    

      


Both attributes, on one form
examples/fjkit-demo/app/templates/jobs/page.html
      

    
      
        
{% call form(action=url_for(request, "jobs_start"), target="#job-list",
             hx_indicator="#job-busy",
             hx_disabled_elt="find button[type=submit]") %}
  {% call field_row("field-and-button") %}
    {{ select_field("kind", label="Background job", options=kind_options) }}
    {% call row(gap=2) %}
      {{ button("Start", variant="primary", type="submit", icon_name="play") }}
      {{ spinner(indicator=true, id="job-busy", label="Starting the job") }}
    {% endcall %}
  {% endcall %}
{% endcall %}




  


      

        hx-disabled-elt is the same machinery aimed at a different problem. It sets
        disabled on whatever the selector names for the length of the request and clears it
        after, which is the whole of what stops a double click from advancing a task twice or posting
        two of the same form. The selector takes this, a
        find …/closest … relative form, or an ordinary CSS selector.
      




      
    

      


How they behave
      

    
      
    

      
counted
both are counted, not toggled — htmx keeps a request count per element, so an early reply cannot re-enable a control another request is still using
    
  
    

      
no layout shift
the indicator is hidden with visibility and opacity, never display — it holds its space, so nothing on the page jumps when it appears
    
  
    

      
inherited
both are inherited: put hx-indicator on a container and everything inside it shares one spinner. this and inherit are valid values
    
  
    

      
it tells you
a selector that matches nothing does warn here — The selector "…" returned no matches! — unlike an out-of-band id, which fails silently
    
  

  


      
    

      


Traps worth knowing
      

    
      
    

      
not inside the target
keep the indicator outside the target: an element inside what is being replaced is torn out mid-request, and its id with it
    
  
    

      
the free version
with no hx-indicator at all the class lands on the trigger itself, so .htmx-request styling on a button is the cheapest loading state there is
    
  
    

      
it remembers
htmx marks what it disabled with data-disabled-by-htmx, so a control that was already disabled stays disabled afterwards
    
  
    

      
a fast request
expect some indicators to barely flash. That is the request being fast, not the indicator being broken — the jobs page does its work after the response, which is why the card polls

htmx

      


No HX-Request: the same route answers JSON
A handler returns a model, not markup. One question decides what goes on the wire: does this caller have markup waiting?
      

      
      

        Lesson 02 said the exchange carries no JSON, and of the swap itself that is true. But look
        at what the handler actually returned: a BoardResponse, not a string of HTML.
        @render is what turns one into the other. When the caller is not a browser
        waiting for markup, there is nothing to render into, so the model goes out as JSON.
      

      

        That is render_mode="auto", the default on FjkitConfig. Two things
        decide it, and neither of them is an Accept header: what the route
        is, and whether the request carries HX-Request: true.
        A page route always has markup waiting, because a cold navigation is the request it exists
        for, and answering that with JSON would be a blank browser window. A fragment route only has
        markup waiting when htmx asked for it.
      




    

      


What auto answers
The route decides the first column; the header decides the second.
      

    
      
      

      

        
          

              The route
              HX-Request
              Content-Type
              Body
          

        
                

          @render("tasks/page.html", partial="tasks/_board.html")
          absent
          text/html
          the whole page, shell and all
        

        

          the same route
          true
          text/html
          _board.html on its own — the swap
        

        

          @render("tasks/_board.html")
          absent
          application/json
          BoardResponse, serialised — the route's response_model
        

        

          the same route
          true
          text/html
          _board.html on its own — the swap
        


      

    




  


      

        Read the third row again, because it is the one worth having: every htmx endpoint in
        the app is already a JSON endpoint. GET /tasks/board answers htmx with
        a board, and answers curl with the model behind it. No second route, no
        serialiser, no DTO that drifts from the template. The return annotation is the only
        description of either, so FastAPI has already put BoardResponse in
        /docs.
      



    
      

    

        
        
        
    
        
@router.get("/tasks", name="tasks_page")
@render("tasks/page.html", partial="tasks/_board.html")
def tasks_page(service: ServiceDep, status: Status | None = None) -> BoardResponse:
    # A page route: it names a page and a partial, so it always has markup
    # waiting. A navigation gets the page; htmx gets the board.
    return _board(service, status)


@router.get("/tasks/board", name="tasks_board")
@render("tasks/_board.html")
def tasks_board(service: ServiceDep, status: Status | None = None) -> BoardResponse:
    # A fragment route: it names only a partial. htmx gets the board, and
    # anyone else gets BoardResponse as JSON — the API, at no extra cost.
    return _board(service, status)

Overriding it
      

    
      
    

      
force HTML
mode="html" on the decorator — a fragment that must never serialise
    
  
    

      
force JSON
mode="json" — a route that is an API and nothing else, even to htmx
    
  
    

      
app-wide
FjkitConfig(render_mode="html") turns the whole behaviour off
    
  
    

      
no request wins
a route that said html or json is not negotiable — only auto reads the header
    
  

  

      
    

      


Two things to know
      

    
      
    

      
caching
fjkit sets Vary: HX-Request on every reply whose shape depended on the header
    
  
    

      
why it matters
without it a CDN serves a cached fragment into a navigation — a page with no shell, and no error anywhere
    
  
    

      
hx-boosted
a boosted link is htmx doing a navigation: it counts as a browser for this question, so it gets the page, not the partial
    
  
    

      
the naming rule
a template whose name starts with _ is a fragment — the same convention test_conventions.py already enforces
