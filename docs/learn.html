Build the interface where you build the routes

Eleven lessons: how a fjkit app is wired, what htmx sends, how a rebrand works, and the command that fails a build. Every demo below is live.

01

Wiring: config, mount, render

Everything else you write is your app, not your front end.

A fjkit app touches the kit in exactly three places. FjkitConfig holds every knob. mount_fjkit() serves the stylesheet and the vendored JS straight out of the installed package, and builds the Jinja environment once per process. @render names the template a route answers with.

Click through the four files. There is no package.json and no watcher to keep running. examples/fjkit-demo in the repository is the same four files in a working app.

        to the stylesheet and the three vendored scripts, and the header/main/footer skeleton. Below is

The four words this page uses precisely
      

    
      
    

      
markup
HTML text — what a template produces before a browser parses it, like <div id="board">…</div>. When a later lesson says a route "has markup waiting", it means a template is ready to turn the handler's return value into HTML rather than into JSON
    
  
    

      
the shell
ui/shell.html, the figure above: the document around your page — <head>, header, <main>, footer, toaster
    
  
    

      
a fragment
a piece of HTML that is not a whole document: no <!doctype>, no <head>, just the elements. It is what an htmx response carries
    
  
    

      
a partial
the template that renders a fragment. Its file name starts with an underscore, it never extends the shell, and the page and the htmx endpoints both use it — lesson 05
    
  

  










      02
htmx

      


The htmx request and response
The server answers a swap with HTML. Nothing is serialised for it, and no client-side state is kept in sync.
      

      
      

        This is the whole idea, and it is smaller than it looks. An element names the request to make
        and where to put the answer. The server answers with a piece of HTML — the same markup it
        would have put in the page — and htmx drops that piece into the element you named.
      

      

        Nothing is serialised for the swap, nothing is re-rendered on the client, and no state lives
        in two places. Press the button: the request below is real. htmx is loaded on
        this page, and a mock server in the browser plays the FastAPI side.
      




    

      


One round trip
The only thing that changes on the client is the subtree named by hx-target.

      03
htmx

      


hx-target and hx-swap
Two attributes decide everything: which element, and how it is replaced.
      

      
      

        hx-target picks the element.
        hx-swap says what to do with it. This pair
        is where most htmx confusion lives, so try it against a live board. Every combination below
        runs a real request and swaps the real response.
      

      

        outerHTML replaces the target itself, so the response has to include the wrapper.
        innerHTML, the default, replaces what is inside it, so the response must not
        include the wrapper. Mixing the two up gives you a board inside a board.

      05
htmx

      


Partials: one file, page and swap
The page embeds the fragment the htmx endpoint returns — so they cannot drift.
      

      
      

        Now the fjkit half. A partial is any template whose name starts with an underscore. It never
        extends the shell, it declares its own imports, and it wraps itself in the element the swap
        replaces. The full page {% include %}s it; every htmx
        endpoint returns it bare.
      

      

        That is why a fjkit app has no "update the row" code path. Every mutation re-renders the
        whole board partial and swaps it. One definition of what a board looks like, used by the
        first paint and by every request after it. The real files are
        examples/fjkit-demo/app/templates/tasks/ in the repository.
      




    

      


Request
      


        
        

    
      
  
        

        

        





  


      

        Those two handlers name the same file, and the name is the part that misleads.
        _board.html is not one task. It is the entire board — the create
        form, the filter bar, the stats card and every row in the table, wrapped in the one
        <div id="board"> that every control on the page targets. The leading
        underscore means "not a page", not "small".
      

      

        So a click on Advance in row three sends one POST, and what comes back is the board
        with all eight rows re-rendered, one of them now saying Doing. That is the trade fjkit makes:
        you render more HTML than strictly changed, and in exchange there is exactly one definition of
        what a board looks like. Below are the three files, and every htmx attribute in them.
      



    
      

    

        
        
        
    
        
{# tasks/page.html — answers the full GET #}
{% extends "base.html" %}
{% from "ui/layout.html" import page_header %}

{% block content %}
  {{ page_header("Tasks", "Every control here swaps #board.") }}

  {# The first paint. This is the same file POST /tasks answers with. #}
  {% include "tasks/_board.html" %}
{% endblock %}



Extends the shell, writes a heading, and includes the partial. Nothing about the board is described twice.
        
{# tasks/_board.html — the whole board: create form, filters, stats, every row #}
{% from "ui/button.html" import button, button_group %}
{% from "ui/table.html" import table %}
{% from "tasks/macros.html" import task_row, TASK_COLUMNS %}

{# The wrapper is inside the file, because hx-swap="outerHTML" replaces it. #}
<div id="board">

  {% include "tasks/_new_task.html" %}

  {# The filter bar. Each button re-fetches the board with a query string. #}
  {% call button_group() %}
    {% for value, label in status_filters %}
      {{ button(label, size="xs",
                hx_get=url_for(request, "tasks_board") ~ ("?status=" ~ value if value else ""),
                hx_target="#board", hx_swap="outerHTML") }}
    {% endfor %}
  {% endcall %}

  {% call table(TASK_COLUMNS, rows=tasks) %}
    {# A repeated element is a macro, not an include in a loop. #}
    {% for task in tasks %}{{ task_row(request, task, filter_query) }}{% endfor %}
  {% endcall %}

</div>



No extends and no doctype, so this renders standalone — which is what lets an htmx endpoint return it bare.
        
{# tasks/macros.html — one row, and the htmx that fires from it #}
{% macro task_row(request, task, filter_query="") %}
  <tr>
    {{ cell(task.title, tone="strong") }}
    {{ cell(badge(task.status.value | capitalize, variant=task.status_variant)) }}
    {% call row_actions() %}
      {# Advance one task — and get the whole board back. #}
      {{ button("Advance", variant="ghost", size="xs",
                hx_post=url_for(request, "tasks_advance", task_id=task.id) ~ filter_query,
                hx_target="#board", hx_swap="outerHTML",
                hx_disabled_elt="this") }}
      {{ button("", variant="ghost", size="icon-xs", icon_name="trash",
                aria_label="Delete " ~ task.title,
                hx_delete=url_for(request, "tasks_delete", task_id=task.id) ~ filter_query,
                hx_target="#board", hx_swap="outerHTML",
                hx_confirm="Delete this task?") }}
    {% endcall %}
  </tr>
{% endmacro %}



The row is a macro, and it is where the htmx lives: every action points at #board and swaps outerHTML, so the reply is always the whole partial.

  



      
    

      


Why one file covers both
      

    
      
    

      
it is the board, not a row
_board.html renders the form, the filters, the stats and all the rows. A single task is task_row() in macros.html — a macro, because a repeated element is a macro and a partial is what a request answers with
    
  
    

      
the wrapper is in the file
the first line of the partial is <div id="board">. It has to be, because every control says hx-swap="outerHTML": the element being replaced is the wrapper, so the reply has to bring one back
    
  
    

      
one context, built once
both callers need the identical names in the context — tasks, stats, status_filters. The router builds them once, in board(), and both handlers return it
    
  
    

      
the filter travels
filter_query rides along on every row action, so advancing a task while the board is filtered to Doing answers with the board still filtered to Doing
    
  

  


      
    

      


What it costs
      

    
      
    

      
bytes on the wire
the whole board, every time. That is a few kilobytes of HTML the browser parses instead of a diff it does not have to compute — and no client-side model to keep in step
    
  
    

      
when it stops paying
when a board grows past what you want to re-render, the answer is a smaller partial with its own id, not a smarter client. Lesson 06 and lesson 07 are both that answer
    
  
    

      
focus
an outerHTML swap replaces the element the focused input is inside. htmx restores focus by id, so give an input that survives a swap a stable id
    
  
    

      
big boards
templates.page() renders this. Reach for templates.stream() only when the row count is the user's to choose
    
  

  




    

      


The board, live — add, advance, delete
Every control targets #demo-board, and every response is the whole board partial.
      

working…    
      
  
        

        





  


      
    

      


Traps worth knowing
      

    
      
    

      
full page back
returning page.html from an htmx route nests a whole document inside your div — return the partial
    
  
    

      
4xx does not swap
htmx ignores error responses by default. The shell adds 422, and only 422, which is what lets a rejected form come back as the form itself
    
  
    

      
lost wrapper
outerHTML needs the wrapper in the response, or the target disappears
    
  
    

      
stale filter
a row action must carry the active filter, or the swap silently resets the view
    
  
    

      
inherited swap
hx-target and hx-swap are inherited from ancestors. A button inside a card that polls itself with outerHTML inherits that swap, and replaces the element it meant to fill — spell both out on any trigger nested inside another htmx element
    
  

  

      
    

      


Server-side helpers
      

    
      
    

      
HX-Request
the header that tells a route it is answering a swap
    
  
    

      
HX-Trigger
response header that fires a client event — how fjkit raises a toast from a swap, which has no toaster in it
    
  
    

      
HX-Redirect
full-page redirect from inside a swap response
    
  
    

      
hx-swap-oob
one response, several regions — the next lesson
    
  

  











      06
htmx

      


One reply, many regions: hx-swap-oob
hx-target names one element. When one answer has to move six, the other five carry their own address.
      

      
      

        Every swap so far has had one target, and that is enough while the things that change sit
        under one element. The board is a single <div id="board">: every control on
        it points there, and every response is the whole board.
      

      

        A search result is not one thing. One query moves a row of counters above the table, the table
        itself, a progress card, a facet list and a siblings panel in the aside, and a detail panel
        below it — six fragments in three places, and the only element that contains all six is
        <body>. Swapping the body is a page reload with extra steps.
      

      

        So the reply carries the other five out of band — outside the one channel
        hx-target describes. Each of them says where it belongs by carrying the id it is
        going to.
      




      

        Nothing about the trigger is special, and that is the point worth seeing before the reply. One
        input, one hx-get, one hx-target — the same shape as lesson 03. It
        names #search-matches and knows about no other region on the page.
      



    
      

    

        
        
    
        
{# search/page.html — the one control that starts all of this #}
{% call form(action=url_for(request, "search_page"), method="get") %}
  {% call field_row("field-and-button") %}
    {{ text_field("q", label="Search tasks", value=query, type="search",
                  hx_get=url_for(request, "search_page"),
                  hx_trigger="input changed delay:250ms, search",
                  hx_target="#search-matches", hx_swap="outerHTML",
                  hx_push_url="true", hx_indicator="#search-busy") }}
    {{ button("Search", variant="primary", type="submit", icon_name="search") }}
  {% endcall %}
{% endcall %}



hx_* keywords on any fjkit macro become hx-* attributes on the element it emits. The form around it carries action and method, so the same query still works with scripting off.
        
<input class="input" type="search" name="q" id="q"
       hx-get="/search"
       hx-trigger="input changed delay:250ms, search"
       hx-target="#search-matches"
       hx-swap="outerHTML"
       hx-push-url="true"
       hx-indicator="#search-busy">



One target. htmx will replace #search-matches with whatever comes back — and it does not know the reply is about to move five other elements.

  



    

      


What comes back from one keystroke
GET /search?q=cache, answered by one handler and one response model.
      

    
      
        
<div id="search-matches">…</div>                     ← no marker: this is what hx-target gets
<div id="search-stats"    hx-swap-oob="true">…</div>   ← flies to the counters
<div id="search-progress" hx-swap-oob="true">…</div>   ← flies to the aside
<div id="search-facets"   hx-swap-oob="true">…</div>   ← flies to the aside
<div id="search-related"  hx-swap-oob="true">…</div>   ← flies to the aside
<div id="search-detail"   hx-swap-oob="true">…</div>   ← flies below the table




  


      
    

      


What htmx does, in order
      

    
      
    

      
1 — lift
every top-level element carrying hx-swap-oob is lifted out of the response
    
  
    

      
2 — place
each one is matched to the element on the page with the same id and replaces it
    
  
    

      
3 — then the target
whatever is left is swapped into hx-target as usual
    
  

  


      
    

      


Four things to know
      

    
      
    

      
the value
true replaces the matching element; innerHTML, beforeend and the rest of the swap vocabulary all work here too
    
  
    

      
it fails in silence
an id that matches nothing is dropped without a word — no error, no console entry, and that region simply keeps the previous query's numbers
    
  
    

      
top level only
an out-of-band fragment nested inside a wrapper is not one — which is why the reply template is a flat list of includes
    
  
    

      
not the target
never mark the fragment that hx-target names: it would be lifted out too, and the target would be swapped with nothing
    
  

  




      

        On the fjkit side there is no new machinery. The page and the reply
{% include %} the same six partials and differ in one
        variable: the page renders them cold, the reply renders them addressed. Each partial defaults
        the flag itself, so it still renders standalone.
      




    

      


One set of partials, two ways of rendering them
      

    
      
        
{# _results.html — what an htmx request gets #}
{% include "search/_matches.html" %}
{% with oob = true %}
  {% include "search/_stats.html" %}
  {% include "search/_progress.html" %}
  {% include "search/_facets.html" %}
  {% include "search/_detail.html" %}
  {% include "search/_related.html" %}
{% endwith %}

{# _stats.html — and every other region, at the top #}
{% set oob = oob | default(false) %}
<div id="search-stats"{% if oob %} hx-swap-oob="true"{% endif %}>
  …
</div>




  


      

        The payoff is that the page decides where a fragment lives, once. Move the facet card from the
        aside into the main column and the router, the response model and the swap are all unchanged.
        The working files are
        examples/fjkit-demo/app/templates/search/ in the repository — and the next
        lesson is the other half of that same page, because a real screen needs both.
      











      07
htmx

      


One id, many fragments: HX-Trigger
The opposite problem to lesson 06: the trigger produces an id, and each region has a different question to ask with it.
      

      
      

        The last lesson worked because one handler could answer every region at once: one query, six
        fragments, one response model holding all of them. Opening a row on that same page is a
        different shape. The click produces an id, and the panels that care about it each
        need their own query — the detail of that task, the other tasks its owner has. A handler
        answering all of them would have to import every service on the page, and a third panel would
        mean editing it.
      

      

        So the pick answers with its own region — the table, with the row now marked — and sends the id
        out in HX-Trigger. htmx raises that header as a DOM event, and the fragments that
        care listen for it and fetch their own data. The route does not know how many of them there
        are, or that any of them exist. Adding a panel is one more subscriber and no change to any
        route.
      




    

      


The route that picks
A GET, because picking changes nothing on the server. The table is the button's hx-target, so the reply swaps it in band.
      

    
      
        
@router.get("/search/select/{task_id}", name="search_select")
@render("search/_matches.html",
        hx_trigger=lambda task_id: {"task-selected": {"task_id": task_id}})
def select_task(service: ServiceDep, task_id: int, q: str = "") -> MatchesResponse:
    """Mark the row, answer with the table, and tell the panels which id."""
    return _matches(service, q, _selected(service, task_id).id)





  


      

        hx_trigger declares the event. It is a parameter of @render rather
        than a header the handler writes, so it works the same on a route that also renders. A
        callable is resolved per request from the handler's own parameters by name —
        task_id here — plus result, what the handler returned. Returning
        None from it is not an error, so a route can broadcast only sometimes.
      

      

        Nothing else about that route is special. It is an ordinary partial route — one template, one
        response model — with an event attached, and that is what makes the pattern cheap: the swap
        and the broadcast are one round trip, declared in one place.
      

      

        A second action on the same page shows the other half. Advance changes a status, so it raises
        a different event, and a different set of fragments cares.
      




    

      


A second event, from a route that changes something
The reply is the swap — the detail panel is this button's hx-target — and the header is what the other four hear.
      

    
      
        
@router.post("/search/advance/{task_id}", name="search_advance")
@render("search/_detail.html",
        hx_trigger=lambda task_id: {"task-changed": {"task_id": task_id}})
def advance_task(service: ServiceDep, task_id: int) -> DetailResponse:
    """Advance the task, answer with the detail panel, and say what changed."""
    if service.advance(task_id) is None:
        raise HTTPException(status_code=404, detail="task not found")
    return DetailResponse(selected=service.get(task_id))





  


      

        Two events, and each fragment hears the ones it has a reason to. The counters listen for
        task-changed and not task-selected, because picking a task changes no
        count. The facets listen for neither, because advancing one changes no owner and no priority.
        Which broadcasts a fragment hears is the fragment's own decision, and no route knows it
        exists.

        One rule holds this together: the fragment a route answers with must not subscribe to
        the event that route raises. It is already being replaced in band, so hearing the
        event fetches it a second time for the same click. On a fragment that is its own target, that
        never stops. htmx does not catch it, because a subscriber asking for its own URL is what the
        attribute says to do. So the table hears only task-changed and the detail panel
        only task-selected: each is a route's target for one event and a subscriber for
        the other, never both for the same one.
      




    

      


The subscriber
These attributes on every region that cares, and nothing on the ones that do not.
      

    
      
        
{# a panel that needs only the id #}
<div id="search-detail"
     hx-get="/search/detail"
     hx-trigger="task-selected from:body"
     hx-vals="js:{task_id: event.detail.task_id}"
     hx-target="this" hx-swap="outerHTML">…</div>

{# a region that also depends on the search box #}
<div id="search-stats"
     hx-get="/search/stats"
     hx-trigger="task-changed from:body"
     hx-include="[name='q']"
     hx-target="this" hx-swap="outerHTML">…</div>




  


      
    

      


The attributes that matter
      

    
      
    

      
who is listening
from:body — htmx raises the event on the element that made the request, and it bubbles. The panels are nowhere near that element, so they listen where it arrives
    
  
    

      
how the id arrives
hx-vals="js:…" is the one place the id turns back into a query parameter. Reading it out of the event, rather than remembering the selection on the server, keeps the endpoints stateless and two open tabs independent
    
  
    

      
what else it needs
hx-include — for what the event does not carry. The counters count the matches, so they need the search box as well as the id, and a selector fetches it off the page instead of every event carrying it
    
  
    

      
what gets replaced
hx-target="this" — every subscriber replaces itself, so a reply is always one region and the sender never has to know how many regions exist
    
  

  


      
    

      


Four things to know
      

    
      
    

      
send an object
the trigger value must be a JSON object. htmx passes an object through as event.detail and wraps anything else — an array included — as {value: …}, so a listener reading event.detail.task_id finds nothing
    
  
    

      
it fires before the swap
HX-Trigger fires before the swap, which is why the id travels in the event: a hidden input holding the selection would still hold the old one when the subscribers read it. HX-Trigger-After-Swap is the header for the other order
    
  
    

      
inheritance leaks in
hx-vals is inherited, and htmx merges it up the tree on a path that does not consult hx-disinherit. An htmx element inside a subscriber — the row's own title, which is the button that opens it — has to say hx-vals="unset", which is the only value that stops the walk
    
  
    

      
N panels, N requests
N subscribers is N requests. That is the trade: the page fans out instead of the handler fanning in, and hx-sync or a cache is where you pay it back if the queries are expensive
    
  

  




      

        The two lessons do not compete, and the demo does not put them on separate pages. They answer
        different questions, and /search asks both: a query is one question the server
        can answer completely, and a pick is an id that three regions each have a different question
        about.

        The working files are examples/fjkit-demo/app/features/search/ and

        stamps — the table, the detail panel, the siblings panel — while the counters, the progress
        card and the facets sit still. An advance is five, and the facets are then the only card that
        does not move.

htmx

      


While the request is in flight
A swap is a round trip, and nothing stops a second click during it. Two attributes cover the whole of the wait.
      

      
      

        htmx adds the class htmx-request to an element for the length of a request and
        removes it afterwards. Without hx-indicator that element is the one that fired the
        request; with it, it is whatever the selector names. Then this stylesheet — htmx's own, injected
        at startup — does the rest:
      




    

      


The rules htmx injects
Two selectors, comma separated.
      

    
      
        
.htmx-indicator { opacity: 0; visibility: hidden }

.htmx-request .htmx-indicator,
.htmx-request.htmx-indicator { opacity: 1; visibility: visible; transition: opacity 200ms ease-in }




  


      

        The first selector covers an indicator inside the marked element — a spinner in the button
        that was clicked. The second covers an indicator that is itself the marked element, which is
        the shape fjkit uses: spinner(indicator=true) adds htmx-indicator and
        nothing else, so a loading state costs you no CSS, no JavaScript and no round trip to reveal
        it.
      




    

      


Both attributes, on one form
examples/fjkit-demo/app/templates/jobs/page.html
      

    
      
        
{% call form(action=url_for(request, "jobs_start"), target="#job-list",
             hx_indicator="#job-busy",
             hx_disabled_elt="find button[type=submit]") %}
  {% call field_row("field-and-button") %}
    {{ select_field("kind", label="Background job", options=kind_options) }}
    {% call row(gap=2) %}
      {{ button("Start", variant="primary", type="submit", icon_name="play") }}
      {{ spinner(indicator=true, id="job-busy", label="Starting the job") }}
    {% endcall %}
  {% endcall %}
{% endcall %}




  


      

        hx-disabled-elt is the same machinery aimed at a different problem. It sets
        disabled on whatever the selector names for the length of the request and clears
        it after, which is what stops a double click from advancing a task twice or posting two of the
        same form. The selector takes this, a
        find …/closest … relative form, or an ordinary CSS selector.
      




      
    

      


How they behave
      

    
      
    

      
counted
both are counted, not toggled — htmx keeps a request count per element, so an early reply cannot re-enable a control another request is still using
    
  
    

      
no layout shift
the indicator is hidden with visibility and opacity, never display — it holds its space, so nothing on the page jumps when it appears
    
  
    

      
inherited
both are inherited: put hx-indicator on a container and everything inside it shares one spinner. this and inherit are valid values
    
  
    

      
it tells you
a selector that matches nothing does warn here — The selector "…" returned no matches! — unlike an out-of-band id, which fails silently
    
  

  


      
    

      


Traps worth knowing
      

    
      
    

      
not inside the target
keep the indicator outside the target: an element inside what is being replaced is torn out mid-request, and its id with it
    
  
    

      
the free version
with no hx-indicator at all the class lands on the trigger itself, so .htmx-request styling on a button is the cheapest loading state there is
    
  
    

      
it remembers
htmx marks what it disabled with data-disabled-by-htmx, so a control that was already disabled stays disabled afterwards
    
  
    

      
a fast request
expect some indicators to barely flash. That is the request being fast, not the indicator being broken — the jobs page does its work after the response, which is why the card polls
