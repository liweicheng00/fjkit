Plugins

Some things are not a macro. A plugin adds middleware, an exception handler, or a value every template gets — in one object, registered in one place.

01

What a plugin is

Two contribution points, because the kit has two moments.

A macro covers what a page draws. It does not cover what happens before the handler runs, or what every template should know without a route passing it along. Sessions need both. Locales and feature flags need the second. A flash message needs only the first.

A plugin is one object with two optional methods. mount() runs when the app is constructed; extend() runs when the Jinja environment is built. A plugin that only puts a value in every template writes only the second, and one that only touches the request on its way past writes only the first. 

config = FjkitConfig(
    template_dir=APP_DIR / "templates",
    plugins=(auth, flash),
)
mount_fjkit(app, config)

That is the whole registration. mount_fjkit() already reads this config for the static mount and the environment, so a plugin needs no second call and no import order to get right.

The split between the two methods stays visible on purpose. Hiding it would be friendlier until someone's mount() silently never ran.

02

mount(): the app side

Middleware, handlers, routes — attributed to the plugin that added them.

AppSetup is a thin pass-through to FastAPI. What it adds is attribution: a misbehaving plugin is named rather than found by elimination.

AppSetup

add_middleware(cls, **options)

Starlette runs middleware in reverse registration order, so a plugin listed later in plugins= wraps the ones before it

add_exception_handler(exc, handler)

note that an exception raised inside middleware never reaches one — Starlette's handler layer sits inside the user stack

include_router(router)

for a plugin that ships endpoints of its own

mount_static(url, directory)

for a plugin that ships assets, mounted under a name derived from the plugin's

warn(message)

startup configuration checks; the message is prefixed with the plugin's name and raised as PluginWarning

app, config

the live FastAPI app and the FjkitConfig, for the checks the two above cannot express

warn() is for the combinations only the plugin can recognise — an in-memory session store under a production config, say. That works on your laptop and logs users out at random behind four workers, and nothing in the traceback points at the cause.

03

extend(): Jinja, and every render

The per-request context is the part that was missing.

FjkitConfig.globals is resolved once per process. That is right for a version string and useless for the signed-in user. add_context_processor() is the other half: a callable run once per render, with the live request.

EnvSetup

add_template_dir(path)

searched after the app's templates and before the kit's — a plugin may replace a kit macro, never a file the app wrote

add_global(name, value)

one value for the whole process

add_filter(name, fn)

a Jinja filter

add_context_processor(fn, provides=[…])

merged into every template's context, once per render

def extend(self, setup: EnvSetup) -> None:
    setup.add_context_processor(
        lambda request: {"session": getattr(request.state, "auth", None)},
        provides=["session"],
    )

Two constraints, both deliberate. A processor is synchronous: it runs inside Templates.page(), which a def handler reaches from the threadpool. A plugin needing I/O does it in middleware and leaves the result on request.state, which is what the line above reads.

provides= is required rather than inferred. Without it, two plugins fighting over user are discoverable only by rendering a page and noticing. With it, the clash is a startup error naming both.

add_template_dir() is how a plugin that ships UI ships it; section 09 is the worked example. One thing goes with it: the Tailwind build scans an explicit list of directories in fjkit.css, so a plugin inside the kit adds its template directory to that list. Miss it and nothing fails — the templates render, every utility class in them is absent from the stylesheet, and the page looks broken.

04

Order, collisions, and limits

Everything a plugin can collide over fails at startup, not in production.

Template search order

First match wins.

Searched Belongs to May shadow
1 the app's template_dir everything — this is fjkit eject
2 each plugin, in plugins= order the kit's macros, never the app's files
3 the kit nothing

Refused at startup

two plugins with one name

they would collide on request.state.<name> and make every later error ambiguous

two plugins claiming one global, filter or context key

the error names both, and says to rename one or drop one

a context key a processor did not declare

caught under strict_undefined, so it surfaces in development

What a plugin cannot do

inject markup

There is no hook to inject markup into the shell. With one, any plugin could put a <script> on every page, and both "no build step on your side" and the closed vocabulary would leave through it. A plugin that ships UI ships templates, and they pass fjkit check like everything else.

depend on another plugin

order is the order you wrote; there is no resolution step, because nothing has needed one yet

open a connection at startup

no lifespan hook — a plugin takes a client the app already built, which is why RedisStore has a client parameter

05 fjkit.auth

The auth plugin

The browser holds a cookie. The server holds the token.

The first plugin in the box, and the reason the seam exists. The browser gets one opaque, signed, HttpOnly cookie. The access token, the refresh token and your claims stay in a session store on the server.

This is what an htmx app wants: no htmx:configRequest hook attaching a header, no refresh-and-retry glue, no token in the DOM. The browser sends the cookie on every request because that is what browsers do. 

auth = AuthPlugin(
    secret=os.environ["FJKIT_SECRET"],
    store=RedisStore(redis.from_url(REDIS_URL)),
    source=MyOIDCSource(),
    trusted_origins=["https://app.example.com"],
)
mount_fjkit(app, FjkitConfig(template_dir=…, plugins=(auth,)))

Three seams, replaceable independently

SessionStore

MemoryStore for development, RedisStore for production, or your own — five async methods

TokenSource

how credentials become a session: a password check, an OIDC code exchange, an upstream token swap. LocalSource is the default and has no upstream at all

Csrf

a cookie is an ambient credential, so CSRF returns. SameSite=Lax plus an exact Origin comparison — the two miss different things

Routes see none of it. Put Depends(auth.required) on a router and its handlers keep the signatures they had; the session is on request.state.auth, and in every template as session.

How an anonymous request is refused

The same question @render asks about the wire, asked about how to say no.

Who asked Answer Why not 401
htmx 401 + HX-Redirect — htmx acts on HX-Redirect before it reads the status, so this one is both
a browser navigation 303 a 401 with no body is a blank page; people want the login form
a script, curl, a service 401 — this is the caller 401 is for

Only the middle row cannot be a 401: a plain navigation has no way to act on one, so it would land on a blank page. htmx is the interesting case. It reads HX-Redirect and returns before it looks at the status code, so the status stays honest while the browser still moves the whole page.

A navigation is recognised by Sec-Fetch-Mode: navigate, or failing that by Accept mentioning text/html. Anything else is the caller a route in render_mode="auto" answers in JSON. The 401 carries no WWW-Authenticate, although RFC 9110 requires the field: every registered scheme is wrong here, and Basic would make the browser open its own credential dialog — the login form this plugin exists to replace.

Worth knowing before you reach for it

one store read per request

the price of revoking a session by deleting a row, and of keeping refresh tokens off the wire

refresh is locked

four swaps firing at once would otherwise send four refreshes, and an upstream that rotates refresh tokens revokes the family when the second arrives

the session id does not change on refresh

concurrent swaps would each return a different Set-Cookie, the last would win, and the rest would be orphaned

login routes are async def

they await the store, and a real TokenSource awaits an identity provider. Routes that only render stay def

06 fjkit.messages

Messages: three layers

One message, three layers — and only the top one needs a secret.

Showing a line of text to the person who made this request is not one feature but three, stacked: the surface that draws it, the way it gets onto a response, and the way it survives a redirect. Only the last needs a signing secret, which is why one of them is a plugin and the other two are not.

The three layers

Two of them are core, because neither of them needs anything from you.

Layer Where it lives Core or plugin
the surface ui/feedback.html's toaster region, drawn by ui/shell.html on every page whether or not anything is in it core
onto this response fjkit.messages — messages.add(request, …), from a route, a service or an exception handler core
past a redirect fjkit.flash — a short-lived signed cookie, section 07 plugin 
from fjkit import messages

messages.add(request, "Saved", category="success")
messages.add(request, "Could not save", "The title is required.", category="error")

No plugin, no secret, no configuration — which is the point of drawing the line here. Signing a cookie needs a secret, and requiring one from every app, including one with no forms and nothing to say, would end mount_fjkit(app) working with no config at all. Everything that does not need a secret is core.

The third layer is not a superset of the second either. A redirect replaces the page, so the document that would have shown the message is gone before the response arrives, and a cookie is the only thing that crosses. On a response that is not a redirect, that same cookie is a round trip for a message about to be rendered anyway. So the two are layered rather than merged: FlashPlugin queues into fjkit.messages, and the shell has one loop instead of one per delivery mechanism.

How it reaches the browser

@render picks the channel. The caller never has to know which.

What the response is The channel What draws it
a full page render the context the shell's toaster region, straight into the markup
a fragment, an htmx swap HX-Trigger the shell's listener, which turns the event back into a toast

A header rather than markup, because a fragment has no toaster in it: an htmx swap replaces one region, and the region a toast belongs in is elsewhere on the page. It also works on a response htmx will not swap at all. htmx reads HX-Trigger in handleAjaxResponse before it consults responseHandling for the status code, so a 422 or a 500 can still raise a toast on the page the person is looking at. That is the entire delivery mechanism for section 08.

Worth knowing

fjkit_messages() is a global, not a context key

so a route passes nothing in, and a page that has never heard of messages still shows one

consumed by being iterated

a template that loops over the queue marks it delivered; asking whether there is anything to show does not, because that is not showing it. Section 07 depends on the distinction

HX-Trigger is merged, not replaced

a handler that set an event of its own keeps it — dropping it because a toast happened to be queued is a bug that only appears when both are in play

category

info, success, warning, error — a meaning, not a colour. toast() maps each to an icon and a timeout and fjkit.css maps each to a role token, so "error is red" is decided once and survives a rebrand

07 fjkit.flash

The flash plugin

A message that outlives the response that raised it.

A redirect loses a message. HX-Trigger names an event for the page to fire, and the page is replaced before the header arrives; a plain navigation involves no JavaScript at all. The cookie jar is the only thing that crosses.

So a flash is written as a short-lived signed cookie on the response that redirects, read back on the request that lands, queued into fjkit.messages like any other message, and cleared once it has been shown — which is why it appears once and not again on reload. The toaster region in ui/shell.html is already there and already draws that queue, so registering the plugin is the entire setup and no template in your app changes. 

flash = FlashPlugin(secret=os.environ["FJKIT_SECRET"])
auth = AuthPlugin(secret=…, trusted_origins=…, flash=flash)

config = FjkitConfig(template_dir=…, plugins=(flash, auth))

auth is handed the flash rather than importing it. Neither plugin depends on the other: auth works without one, and a route that just saved something wants flash.add(response, "Saved") with no session in sight. The app connects them, for the same reason there is no dependency resolution in section 04.

It has no Jinja side: no extend(), and not one context key of its own. The cookie is queued into fjkit.messages from middleware, so a template never learns that a message arrived by cookie rather than from the handler it is rendering. That is what the layering in section 06 buys — one loop in the shell, not one per delivery mechanism.

The interesting half is when the cookie is cleared: once messages.shown(request) is true, meaning a template iterated the queue or the queue was serialised into an HX-Trigger. A page load fires more requests than the page — an htmx poll, a prefetch — and if "shown" meant "this request carried the cookie", any of them would eat the message and leave the page it belonged to empty. 

def mount(self, setup: AppSetup) -> None:
    setup.add_middleware(_FlashMiddleware, plugin=self)

# what that middleware does, on the way in and on the way back out:
carried = self.plugin.load(request)
if carried:
    messages.extend(request, carried)      # queued like any other message

response = await call_next(request)
if carried and messages.shown(request):
    self.plugin.clear(response)            # only once it reached a page

Raise one from anywhere — flash.add(response, "Saved", category="success") — and it appears as a toast on whatever page the browser lands on next, with no route on that page knowing anything about it. That is the test of whether something should be a plugin at all: could a route have passed it instead? Here it could not, because the route that raises the message is not the route that renders it.

Duck-typed, not inherited

name

a str attribute — required, and the only one

mount / extend

implement either, both, or neither; missing ones are simply not called

no base class

Plugin is a Protocol, so a plugin never imports fjkit to be one

08 fjkit.errors

When a form is rejected

A rejected form used to be a screen of JSON. Now it says what was wrong, under the field, and no route asked for that.

FastAPI answers a rejected form with {"detail":[{"type":"missing",…}]} and a 422. For an API that is right. For a page it is nothing: htmx does not swap a 4xx, so the person filling the form watches nothing happen, and a plain POST lands them on a screen of JSON.

The fix is to notice what that reply already is. It names every field that failed, under the string the form posted it as, with a message a person can read — and the form is still on the page, with everything the person typed still in its controls. Nothing has to be rendered again, remembered, or rebuilt. So mount_fjkit() sends the 422 back as it is, and one script the shell loads, js/errors.js, writes each message under its field. Every handler keeps the signature FastAPI wrote for it, and no route names a template for its rejected state, because there is nothing to render.

What each caller gets

The same question @render asks about the wire, asked about a submit that was refused.

Who asked Answer Why
htmx FastAPI's 422, drawn by the page the form is still there; the script writes each message under the control its loc names, and what was typed stays put
a browser navigation 422 and a page a plain <form method="post"> has left the page, so errors/page.html is rendered through your own shell
a script, curl, a service FastAPI's own reply — byte for byte, with the status it always had. The same bytes as the first row; only the reader differs

The last row is the one worth saying out loud. A caller that did not ask for markup keeps {"detail": …}, because turning an API's error into an HTML page would be a worse bug than the one this fixes. The first row is the same bytes, which is the whole design: an endpoint that is also somebody's API has one error contract, and the page reads it the way any other client would.

That asks one thing of a route, and it is what FastAPI already asks: 

@router.post("/tasks", name="tasks_create")
@render("tasks/_board.html")
def create_task(service: ServiceDep, payload: TaskCreate) -> BoardResponse:
    service.create(payload)
    return _board(service)
The model is the signature. Its fields, its limits and its OpenAPI schema are one declaration, and a rejected one is FastAPI's to report — under body, with the field's name.
{% call form(action=url_for(request, "tasks_create"), target="#board",
             reset_on_success=true, encoding="json", id="new-task") %}
  {{ text_field("title", label="New task", required=true) }}
  {{ select_field("priority", label="Priority", options=priority_options,
                  selected="normal") }}
{% endcall %}
One form, written once, with nothing about errors in it. The script finds each control by name and the paragraph under it by aria-describedby — the wiring every field macro already does.

Keeping what was typed costs nothing, because nothing touches it. The old answer to a 422 was to render the form again with the values echoed back, and it worked until a field held more than one value, or the form needed something only the handler that never ran could have built. Both problems disappear when the form is not rendered again.

A message with no field to land on — a whole-model rule, a body that could not be parsed, a bad path segment — is raised as a toast, through the event fjkit.messages uses. The next request from the same form clears what the last one said, so an accepted resubmit leaves no stale rejection on screen.

The rest of the surface

a ValidationError your own code raised

left to travel, on purpose. It has the same shape as a rejected form and is not one: it is equally what Task(**row) failing three layers down in a service looks like, and drawing a bug as a friendly message hides it behind an apology about a field nobody filled in. Declare the model in the signature and FastAPI raises the request-scoped error that is handled

catch_unexpected_errors

off by default, and that default is the useful one: in development a traceback in the terminal beats a tidy apology in the browser. FjkitConfig.for_production() turns it on, with the other two dev-only knobs. The 422 handler is installed either way, because a rejected form is not a bug

unexpected_error

the words that toast says. Leave it and the kit says <em>Something went wrong</em>; set a <code>Message</code> to change them once, or a callable <code>(request, exc) -&gt; Message</code> to pick them per exception. Choose the words from the exception — never put <code>str(exc)</code> in them, that is the inside of your app

errors/page.html

the page a failed navigation lands on. Replace it by writing a file at the same path in your own template directory — the same shadowing fjkit eject uses, so there is no separate custom-error-page mechanism to learn

js/errors.js

the third and last file every page loads, after htmx and Basecoat. It listens to htmx:beforeSwap, so a 422 that is not FastAPI's list — a route answering with markup of its own — is left alone

09 fjkit.apidocs

The API console

Sign in on the page, and every call below goes out as you.

Swagger UI's Authorize dialog can express only what an OpenAPI document can describe: an API key, an HTTP scheme, an OAuth2 flow. An app whose sessions are section 05's — a signed HttpOnly cookie over a server-side token — is none of those. Its Try it out could not send one anyway: it runs fetch() in the browser, and that cookie is the one JavaScript may not read.

So both halves move to the server. Signing in is a Python object your app supplies, which for a fjkit.auth app is the TokenSource your login page already calls. Sending a request is an in-process replay through your own app, carrying the caller's own cookie through the whole middleware stack, so token refresh, revocation and the Origin check are the ones you already wrote rather than a second implementation living in a docs page. 

docs = ApiDocsPlugin(title="Board API", home_url="/")

mount_fjkit(app, FjkitConfig(template_dir=…, plugins=(auth, docs)))

That is the whole of the wiring. No route to write, no template to render, no static file to serve: the plugin brings its own router and templates, and finds the AuthPlugin in the same plugins tuple to wire the sign-in panel to. Pass flow= instead when the app authenticates some other way, and FastAPI(docs_url=None, redoc_url=None) when you want only this one.

The half Swagger cannot do

Both read the same /openapi.json. They differ after that.

Question Swagger UI fjkit.apidocs
Signing in the four schemes the document can describe your app's own code — a Python object
Where the call runs in the browser, as fetch() in the app, as an ASGI replay
What it carries what JavaScript can reach your session cookie, HttpOnly and all
Gating the page not its job dependencies=[Depends(auth.required)]

What each argument decides

url="/api-docs"

where the page lives. Not /docs: FastAPI has claimed that before a plugin mounts, the first route registered wins, and a docs page that silently never renders is worse than a different URL — so the plugin warns at startup if the path is taken

flow=

how someone signs in from the page. Defaults to the AuthPlugin sharing the config, and to a panel that only says "anonymous" when there is none

dependencies=

put on every route the plugin adds — this is how the page is gated. Empty is right for a public API and wrong for an internal service

try_it=False

renders the reference and drops the console, for an environment where replaying a request server-side is not acceptable

home_url=

a way back out, in the sidebar's footer. The operation list has taken the sidebar, so without it the page is a room with no door

It is also the kit's worked example of section 03's add_template_dir(). The console's templates live beside its code, in fjkit/apidocs/templates/apidocs/, and extend() hands that directory to the loader. The inner apidocs/ keeps the names at apidocs/page.html, which lets your app replace any one of them by writing templates/apidocs/<name>.html of its own — the app's directory is searched first.

Worth knowing before you reach for it

its routes are out of your document

include_in_schema=False, for the same reason FastAPI keeps /docs out of it: these are a way of reading the API, not part of it

a call is capped

64 KB of body and 30 seconds, both arguments. The console is a reading tool, not a load generator

form bodies become fields

an Annotated[str, Form()] route gets one input per field rather than a text box, so nobody is asked to hand-write urlencoding. A JSON body stays a single editable example, prefilled from the schema

nothing on the page can read the credential

signing in is a form your app defines, not a box to paste a token into — which is the same property that makes the cookie worth having
