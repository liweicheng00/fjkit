Plugins

有些東西不是 macro。plugin 加的是 middleware、exception handler，或是每個模板都該拿到的值—— 一個物件，一個地方註冊。

01

plugin 是什麼

兩個貢獻時機，因為 kit 真的有兩個時機。

macro 管的是一頁畫出什麼。它管不到 handler 執行之前發生的事，也管不到「每個模板都該知道、 但不該由每條路由傳過去」的東西。session 兩者都要；語系與 feature flag 只要後者； flash 訊息只要前者。

plugin 是一個物件，兩個方法都可選。mount() 在 app 建構時執行， extend() 在 Jinja environment 建立時執行。只想給每個模板一個值的 plugin， 就只寫後面那個；只想在請求經過時動點手腳的，就只寫前面那個。 

config = FjkitConfig(
    template_dir=APP_DIR / "templates",
    plugins=(auth, flash),
)
mount_fjkit(app, config)

註冊就這樣而已。mount_fjkit() 本來就要讀這份 config 來掛靜態檔與建 environment，所以 plugin 不需要第二個呼叫，也沒有 import 順序要記。

分成兩個時機是刻意讓它看得見的。藏起來會比較友善——直到某個人的 mount() 靜悄悄地沒有執行為止。

02

mount()：app 那一側

middleware、handler、路由——而且都記在加它的那個 plugin 頭上。

AppSetup 基本上就是 FastAPI 的轉手。它多做的事是署名：出問題的 plugin 會被 指名，而不是靠一個一個拔掉來找。

AppSetup

add_middleware(cls, **options)

Starlette 依註冊的反序執行 middleware，所以 plugins= 裡排在後面的 plugin 包在前面那些的外層

add_exception_handler(exc, handler)

注意 middleware 裡拋出的例外永遠到不了 handler——Starlette 的 handler 那一層在使用者 middleware 的內側

include_router(router)

給自帶端點的 plugin

mount_static(url, directory)

給自帶資產的 plugin，掛載名稱由 plugin 名字衍生

warn(message)

啟動期的設定檢查；訊息會冠上 plugin 名稱，以 PluginWarning 發出

app, config

活的 FastAPI app 與 FjkitConfig，給上面兩個表達不了的檢查用

warn() 是給「只有這個 plugin 認得出來」的組合用的。例如正式設定配上記憶體版 session store：在你的筆電上完全正常，換到四個 worker 後面就會隨機把人登出，而且 traceback 裡沒有任何一行指向原因。

03

extend()：Jinja 與每一次渲染

per-request 的 context，是原本缺的那一塊。

FjkitConfig.globals 每個 process 只算一次。對版本字串來說剛剛好，對「現在登入 的是誰」來說毫無用處。add_context_processor() 是另外那一半：每次渲染執行一次， 拿得到當下的 request。

EnvSetup

add_template_dir(path)

搜尋順序排在 app 的模板之後、kit 的之前——plugin 可以蓋掉 kit 的 macro，永遠蓋不掉 app 自己寫的檔案

add_global(name, value)

整個 process 一個值

add_filter(name, fn)

一個 Jinja filter

add_context_processor(fn, provides=[…])

併進每個模板的 context，每次渲染一次

def extend(self, setup: EnvSetup) -> None:
    setup.add_context_processor(
        lambda request: {"session": getattr(request.state, "auth", None)},
        provides=["session"],
    )

兩個限制，都是刻意的。processor 必須是同步的：它在 Templates.page() 裡執行，而那是 def handler 從 threadpool 進來的。 需要 I/O 的 plugin 在 middleware 裡做完，把結果留在 request.state 上——上面那 一行讀的正是這個。

provides= 是強制宣告而不是自動推得。沒有它，兩個 plugin 默默搶同一個 user，只能靠渲染一頁然後剛好注意到才會發現；有了它，衝突是一個點名雙方的啟動 期錯誤。

add_template_dir() 是「一個帶 UI 的 plugin 怎麼把 UI 帶進來」的答案，第 09 節 就是那個範例。它有一個附帶條件：Tailwind 的掃描範圍是 fjkit.css 裡一份明列的 目錄清單，所以 kit 內建的 plugin 要把自己的模板目錄加進那份清單。漏掉不會有任何失敗——模板 照樣渲染，裡面每一個 utility class 都不在樣式表裡，頁面就只是看起來壞掉。

04

順序、碰撞與界線

所有可能撞在一起的東西，都在啟動時炸，不會留到正式環境。

模板搜尋順序

先找到的贏。

順序 屬於 可以蓋掉
1 app 的 template_dir 全部——這就是 fjkit eject
2 每個 plugin，依 plugins= 的順序 kit 的 macro，永遠不含 app 的檔案
3 kit 沒有

啟動時就拒絕

它們會在 request.state.<name> 上撞在一起，之後每一則錯誤訊息都變得沒辦法分辨

錯誤訊息會點名雙方，並要你改名或拿掉一個

在 strict_undefined 下會被抓到，所以是在開發階段浮現

沒有任何一個 hook 能把 markup 塞進 shell。有的話，任何 plugin 都能在每一頁放一段 <script>——「你這端零建置」與封閉詞彙表會同時從那道側門走掉。要出 UI 的 plugin 出的是模板，而且跟其他東西一樣得過 fjkit check。

依賴另一個 plugin

05 fjkit.auth

auth plugin

瀏覽器拿 cookie，token 留在伺服器。

內建的第一個 plugin，也是這個接縫存在的理由。瀏覽器只拿到一個不透明、簽名過的 HttpOnly cookie；access token、refresh token 與你的 claims 全部留在伺服器端的 session store 裡。

這正是 htmx app 要的形狀。不需要 htmx:configRequest 去掛 header、不需要 refresh 重試的膠水、DOM 裡沒有 token——瀏覽器每個請求都會帶上 cookie，因為瀏覽器本來就會。 

auth = AuthPlugin(
    secret=os.environ["FJKIT_SECRET"],
    store=RedisStore(redis.from_url(REDIS_URL)),
    source=MyOIDCSource(),
    trusted_origins=["https://app.example.com"],
)
mount_fjkit(app, FjkitConfig(template_dir=…, plugins=(auth,)))

三個各自可換的接縫

SessionStore

開發用 MemoryStore、正式用 RedisStore，或你自己的——五個 async 方法

TokenSource

憑證怎麼變成 session：比對密碼、OIDC code 交換、跟上游換 token。預設的 LocalSource 根本沒有上游

Csrf

cookie 是 ambient credential，所以 CSRF 回來了。SameSite=Lax 加上精確的 Origin 比對——兩者漏掉的東西不一樣

路由完全看不到這些。在 router 上掛 Depends(auth.required)，底下的 handler 簽名一個字都不用改；session 在 request.state.auth 上，在每個模板裡叫 session。

未登入的請求怎麼被拒絕

@render 拿來決定線上格式的那個問題，換個角度問：該怎麼說不。

誰在問 回什麼 為什麼不是 401
htmx 401 + HX-Redirect ——htmx 在讀狀態碼之前就處理 HX-Redirect，所以這一格兩者兼得
瀏覽器導覽 303 沒有 body 的 401 就是一片空白；人要的是登入表單
腳本、curl、另一個服務 401 ——401 就是為這個呼叫端存在的

只有中間那一列不能是 401：一般導覽沒有任何機制可以對它做出反應，只會停在一片空白上。 htmx 那一列才有意思——它處理完 HX-Redirect 就 return，還沒讀到狀態碼， 所以狀態碼可以誠實，而瀏覽器照樣整頁移動。導覽的判定是 Sec-Fetch-Mode: navigate， 沒有的話退而看 Accept 有沒有提到 text/html；其餘都是 render_mode="auto" 下會拿到 JSON 的那個呼叫端。那個 401 不帶 WWW-Authenticate：RFC 9110 要求這個欄位，但所有已註冊的機制在這裡都是錯的。 Basic 會讓瀏覽器跳出它自己的帳密對話框，而那正是這個 plugin 要取代掉的登入表單。

動手之前值得知道的

每個請求一次 store 查詢

這是「刪一筆就能撤銷 session」與「refresh token 永不上線」的代價

refresh 有鎖

否則同時發出的四個 swap 會送出四次 refresh，而有輪替的上游在第二次到達時就撤銷整個 family

refresh 期間不換 session id

換了的話並行的 swap 會各帶回一張不同的 Set-Cookie，最後一張贏，其餘變孤兒

登入路由是 async def

它們要 await store，真正的 TokenSource 還要 await 身分提供者。只負責渲染的路由維持 def

06 fjkit.messages

訊息：三層

一則訊息，三層——而且只有最上面那層需要 secret。

「給發出這次請求的那個人看一行字」不是一個功能，是三個疊起來的：畫出它的表面、讓它搭上這個 回應的方法，以及讓它活過一次轉址的方法。只有最後一個需要簽章用的 secret，而那正是這三層裡 只有一個是 plugin、另外兩個是核心的全部理由。

三層

其中兩層是核心，因為它們不需要你給任何東西。

層 住在哪裡 核心還是 plugin
表面 ui/feedback.html 的 toaster 區域，由 ui/shell.html 在每一頁畫出來——裡面有沒有東西都畫 核心
搭上這個回應 fjkit.messages——messages.add(request, …)，路由、service、exception handler 都可以叫 核心
跨過一次轉址 fjkit.flash——一個短命的簽名 cookie，第 07 節 plugin 
from fjkit import messages

messages.add(request, "Saved", category="success")
messages.add(request, "Could not save", "The title is required.", category="error")

沒有 plugin、沒有 secret、沒有任何設定——線畫在這裡就是為了這個。簽一顆 cookie 需要 secret， 而要求每一支 app 都準備一個（包括一支沒有表單、也沒有話要說的 app），就等於宣告 mount_fjkit(app) 不再是零設定就能跑。凡是不需要 secret 的，都留在核心。

而第三層也不是第二層的超集合。轉址會把整頁換掉，所以本來要顯示訊息的那份文件，在回應抵達之前 就不在了，唯一跨得過去的只有 cookie。但對一個不是轉址的回應來說，同一顆 cookie 就是 錯的工具——為了一則馬上就要被渲染出來的訊息多跑一趟。所以兩者是疊起來而不是合而為一： FlashPlugin 把 cookie 排進 fjkit.messages，於是 shell 裡只有一個 迴圈，而不是每種送達方式各一個。

它怎麼到瀏覽器

通道由 @render 決定，呼叫端從頭到尾不需要知道是哪一條。

這個回應是什麼 走哪條通道 誰把它畫出來
整頁渲染 context shell 的 toaster 區域，直接寫進 markup
一段 fragment，一次 htmx swap HX-Trigger shell 裡那支監聽器，把事件變回一個 toast

走標頭而不是 markup，因為 fragment 裡沒有 toaster：一次 htmx swap 換掉的是一個區域，而 toast 該待的那個區域在頁面上的別處。它也能用在 htmx 根本不會 swap 的回應上——htmx 在 handleAjaxResponse 裡讀 HX-Trigger 的時機，早於它去查 responseHandling 決定這個狀態碼要不要換內容，所以一個 422 或 500 照樣能在使用者 正在看的那一頁上跳出 toast。第 08 節整套送達機制就是這個。

值得知道的幾件事

fjkit_messages() 是 global，不是 context key

所以路由什麼都不用傳，一頁從沒聽過 messages 的模板照樣顯示得出來

靠被迭代來消耗

有模板迭代過那個佇列，才算送達；只是問「裡面有沒有東西」不算，因為那不是把它顯示出來。 第 07 節整個依賴這個區別

HX-Trigger 是合併，不是覆蓋

handler 自己設的事件會留著——只因為剛好排了一個 toast 就把它丟掉，是那種兩邊同時出現才會現形的 bug

category

info、success、warning、error——是意義， 不是顏色。toast() 把每一種對到一個圖示與一段停留時間，fjkit.css 把每一種對到一個角色 token，所以「錯誤是紅的」只決定一次，而且換品牌時活得下來

07 fjkit.flash

flash plugin

一則活得比產生它的那個回應更久的訊息。

轉址是訊息的墳場。HX-Trigger 是叫頁面去觸發一個事件，但頁面在那個標頭抵達之前 就被換掉了；一般導覽更是從頭到尾沒有 JavaScript 參與。唯一跨得過去的只有 cookie。

所以 flash 是一個短命的簽名 cookie：在轉址的那個回應上種下去，在落地的那個請求上讀回來， 跟其他訊息一樣排進 fjkit.messages，並在真的被顯示過之後才清掉——這就是它只出現 一次、重新整理不會再跳的原因。ui/shell.html 裡的 toaster 區域本來就在，也本來就 在畫那個佇列，所以註冊 plugin 就是全部的設定，你的模板一個字都不用改。 

flash = FlashPlugin(secret=os.environ["FJKIT_SECRET"])
auth = AuthPlugin(secret=…, trusted_origins=…, flash=flash)

config = FjkitConfig(template_dir=…, plugins=(flash, auth))

auth 是被交給 flash，而不是自己 import 它。兩個 plugin 誰也不依賴誰——auth 沒有 flash 也能跑，而一條剛存好資料的路由想要的是 flash.add(response, "Saved")，跟 session 毫無關係。把它們接起來的是 app， 這也是第 04 節裡沒有相依解析的同一個理由。

它在 Jinja 那一側什麼都沒有——沒有 extend()，也沒有任何屬於自己的 context key。 cookie 是在 middleware 裡排進 fjkit.messages 的，所以模板永遠不會知道這則訊息 是搭 cookie 來的、而不是它正在渲染的那個 handler 給的。這就是第 06 節那個分層換來的東西： shell 裡一個迴圈，而不是每種送達方式各一個。

有意思的是那顆 cookie 什麼時候被清掉，答案是「等到 messages.shown(request) 為真」——也就是等到有模板迭代過那個佇列，或佇列被序列化進 HX-Trigger。一次頁面 載入發出的請求不只頁面本身——htmx 的輪詢、prefetch 都算——如果「顯示過」的定義是「這個請求 帶了那顆 cookie」，其中任何一個都會把訊息吃掉，讓它本來該出現的那一頁空著。 

def mount(self, setup: AppSetup) -> None:
    setup.add_middleware(_FlashMiddleware, plugin=self)

# 那支 middleware 進來時與出去時做的事：
carried = self.plugin.load(request)
if carried:
    messages.extend(request, carried)      # 跟其他訊息一樣排進去

response = await call_next(request)
if carried and messages.shown(request):
    self.plugin.clear(response)            # 真的到過某一頁之後才清

在任何地方發一則——flash.add(response, "Saved", category="success")——它就會 出現在瀏覽器接下來落地的那一頁上，長成一個 toast，而那一頁的路由對它一無所知。這也是判斷 一樣東西該不該做成 plugin 的標準：這個值，路由自己傳得過去嗎？這裡傳不過去，因為發出訊息 的那條路由，不是渲染它的那條。

鴨子型別，不是繼承

name

一個 str 屬性——必要，而且只有這一個

mount / extend

要寫哪個都行，兩個都不寫也行；沒有的那個就不會被呼叫

沒有基底類別

Plugin 是 Protocol，所以一個 plugin 不需要 import fjkit 才能成為 plugin

08 fjkit.errors

表單被退回的時候

表單被退回，以前換來的是一整頁 JSON。現在它會說哪裡不對，就標在欄位下面，而且沒有任何一條路由要求過。

FastAPI 對一份被退回的表單回的是 {"detail":[{"type":"missing",…}]} 加一個 422。 對 API 來說這完全正確；對一頁畫面來說它等於什麼都沒有：htmx 預設不會 swap 4xx，所以正在填 表單的人看到的是「按了沒反應」，而一般的 POST 則會把他丟到一整頁 JSON 上。

解法是看清楚那個回應本來就是什麼。它把每個失敗的欄位都點了名，用的正是表單送出時的那個 名字，訊息也是給人讀的——而表單還在頁面上，使用者打過的每一個字都還在控制項裡。沒有任何東西 需要重新渲染、記住、或重建。所以 mount_fjkit() 把 422 原封不動送回去，由 shell 載入的一支 script js/errors.js 把每則訊息寫到它的欄位下面。每個 handler 的簽名 都還是 FastAPI 寫的那個，也沒有任何一條路由得替「被退回」這個狀態指名一個模板，因為根本沒有 東西要渲染。

每種呼叫端拿到什麼

@render 用來決定線上格式的那個問題，換到「一次被拒絕的送出」上再問一次。

誰在問 回什麼 為什麼
htmx FastAPI 的 422，由頁面畫出來 表單還在原地；script 把每則訊息寫到 loc 指名的那個控制項下面，打過的字一個都不動
瀏覽器導覽 422 加一頁畫面 一般的 <form method="post"> 已經離開那一頁了，所以用你自己的 shell 渲染 errors/page.html
腳本、curl、另一個服務 FastAPI 原本的回應 ——一個位元組都不動，狀態碼也是原本那個。跟第一列是同樣的位元組，差別只在誰在讀

最後那一列值得講明白。沒有要 markup 的呼叫端，拿到的還是 {"detail": …}，因為把 一個 API 的錯誤變成一頁 HTML，會是比這裡要修的那個問題更糟的 bug。而第一列是同樣的位元組—— 這正是整個設計。一個同時也是別人 API 的端點只有一份錯誤契約，頁面讀它的方式跟任何其他 客戶端一樣。

這對一條路由的要求只有一件事，而且是 FastAPI 本來就在要求的那件事： 

@router.post("/tasks", name="tasks_create")
@render("tasks/_board.html")
def create_task(service: ServiceDep, payload: TaskCreate) -> BoardResponse:
    service.create(payload)
    return _board(service)
模型就是簽名。它的欄位、限制與 OpenAPI schema 是同一份宣告，被退回時由 FastAPI 來報——放在 body 底下，帶著欄位的名字。
{% call form(action=url_for(request, "tasks_create"), target="#board",
             reset_on_success=true, encoding="json", id="new-task") %}
  {{ text_field("title", label="New task", required=true) }}
  {{ select_field("priority", label="Priority", options=priority_options,
                  selected="normal") }}
{% endcall %}
一份表單，寫一次，裡面沒有任何關於錯誤的東西。script 用 name 找到控制項、用 aria-describedby 找到它下面那個段落——每個欄位 macro 本來就接好的線。

把使用者填過的東西留住是零成本的，因為沒有任何東西碰到它。以前對 422 的答案是把表單重畫一次、 把值回填進去，這一直行得通——直到某個欄位有多個值，或者表單需要某樣只有「那個沒跑過的 handler」才建得出來的東西。表單不再重畫，這兩個問題就一起消失了。

沒有欄位可以落腳的訊息——整個模型層級的規則、解析不了的 body、壞掉的路徑片段——會透過 fjkit.messages 用的同一個事件升成一個 toast。而同一份表單的下一次送出會把上一次 說過的話清掉，所以一次被接受的重送不會把過期的退回留在畫面上。

其餘的表面

你自己的程式碼丟出的 ValidationError

刻意放它走。它跟一份被退回的表單長得一樣，但它不是：它同樣可能是 service 裡三層深的 Task(**row) 爆掉，而把一個 bug 畫成一句親切的訊息，等於用「某個沒人填過的欄位」 的道歉把它藏起來。把模型宣告在簽名上，FastAPI 就會丟出會被接住的那種 request 層級錯誤

catch_unexpected_errors

預設是關的，而這個預設才是有用的那個：開發時終端機裡的一份 traceback，勝過瀏覽器裡一句得體的 道歉。FjkitConfig.for_production() 會把它打開，連同另外兩個只在開發時有意義的 開關。422 那個 handler 不管怎樣都會裝——被退回的表單不是 bug

unexpected_error

那則 toast 說的話。不設就是 kit 自己的一句 <em>Something went wrong</em>；給一個 <code>Message</code> 就一次換掉，給一個 <code>(request, exc) -&gt; Message</code> 的函式就能依例外種類挑句子。用例外來<em>選</em>句子，不要把 <code>str(exc)</code> 放進去——那是你 app 的內部

errors/page.html

導覽失敗時落到的那一頁。在你自己的模板目錄放一個同路徑的檔案就能換掉——跟 fjkit eject 用的是同一套遮蔽，所以沒有另一套「自訂錯誤頁」的機制要學

js/errors.js

每一頁載入的第三個、也是最後一個檔案，排在 htmx 與 Basecoat 之後。它聽的是 htmx:beforeSwap，所以一個不是 FastAPI 清單的 422——某條路由自己回了 markup——會被放過

09 fjkit.apidocs

API 主控台

在這一頁登入，底下每一次呼叫就都是以你的身分送出去的。

Swagger UI 的 Authorize 只能表達 OpenAPI 文件說得出來的東西：API key、HTTP scheme、 OAuth2 flow。而第 05 節那種 session——簽章過的 HttpOnly cookie，token 留在伺服器 ——四種都不是。它的 Try it out 本來也送不出去：那是在瀏覽器裡跑 fetch()， 而那顆 cookie 正好就是不給 JavaScript 讀的那一顆。

所以兩件事都搬到伺服器。登入是一個由你的 app 提供的 Python 物件，對 fjkit.auth 的 app 來說就是登入頁本來就在呼叫的那個 TokenSource。送出請求是在你自己的 app 裡行程內重放，帶著呼叫者自己的 cookie 走完整條 middleware——所以 token 換發、撤銷、Origin 檢查用的都是你已經寫好的那一份，而不是一份住在文件頁裡的第二實作。 

docs = ApiDocsPlugin(title="Board API", home_url="/")

mount_fjkit(app, FjkitConfig(template_dir=…, plugins=(auth, docs)))

接線就這些。沒有路由要寫、沒有模板要渲染、沒有靜態檔要服務：plugin 自己帶路由、自己帶模板， 並從同一個 plugins tuple 裡找出 AuthPlugin 接上登入面板。app 用別的 方式認證時就傳 flow=；只想留這一頁的話， FastAPI(docs_url=None, redoc_url=None)。

每個參數決定什麼

url="/api-docs"

這一頁的位置。不是 /docs：plugin 掛載時 FastAPI 早就把它拿走了，先註冊的路由贏，而一頁默默永遠不會渲染的文件比換個網址更糟——所以路徑被佔用時，plugin 會在啟動時就警告

flow=

怎麼從這一頁登入。預設是同一份 config 裡的 AuthPlugin；沒有的話，面板就只會說 anonymous

dependencies=

加在 plugin 新增的每一條路由上——這就是擋這一頁的方式。留空對公開 API 是對的，對內部服務是錯的

try_it=False

只渲染參考文件、拿掉主控台，給「在伺服器端重放請求不可接受」的環境用

home_url=

側欄頁尾的那條出路。操作清單已經佔走側欄，沒有它這一頁就是一個沒有門的房間

它同時也是第 03 節 add_template_dir() 在 kit 裡的實例。主控台的模板跟它的程式碼 放在一起，在 fjkit/apidocs/templates/apidocs/，由 extend() 把那個 目錄交給 loader。裡面那層 apidocs/ 是讓名字維持 apidocs/page.html 的原因——也就是你的 app 只要寫一份自己的 templates/apidocs/<名稱>.html 就能換掉其中任何一支，因為 app 的目錄排在最前面被搜。

動手之前值得知道

它的路由不在你的文件裡

include_in_schema=False，跟 FastAPI 把 /docs 排除在外是同一個理由：這些是讀 API 的方式，不是 API 的一部分

一次呼叫有上限

body 64 KB、逾時 30 秒，兩個都是參數。主控台是讀 API 的工具，不是壓測工具

form body 會拆成欄位

一條 Annotated[str, Form()] 的路由拿到的是一欄一個輸入框而不是一個文字框，沒有人需要自己手刻 urlencoding。JSON body 則是一份可編輯的範例，內容由 schema 預先填好

這一頁上沒有任何東西讀得到憑證

登入是你的 app 定義的表單，不是一個貼 token 的框——這跟那顆 cookie 值得擁有的是同一個性質
