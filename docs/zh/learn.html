在寫路由的地方，把介面一起寫完

十一課：一支 fjkit app 怎麼接、htmx 實際送出什麼、換品牌怎麼換，以及那個會讓 build 失敗的指令。 底下每個示範都會實際執行。

01

接線：config、mount、templates

接觸點只有三個；其餘寫的都是你的 app，不是前端。

一支 fjkit app 只在三個地方接觸 kit。FjkitConfig 收下所有設定。 mount_fjkit() 從安裝好的套件供應 stylesheet 與 vendored JS， 並在每個 process 建立一次 Jinja environment。@render 指名路由要用的模板。

底下四個檔案可以逐一點開。沒有 package.json，也不需要開著 watcher。 repo 裡的 examples/fjkit-demo 就是同樣這四個檔案，放在一支能跑的 app 裡。 


          

        

      


  


      

        第二個分頁值得配一張圖。base.html 只有四個 block，是因為它 extends 的
        ui/shell.html 已經拿走其餘部分：<head>、
        第一次繪製前就套用深色模式的那支腳本、指向 stylesheet 與三支 vendored 腳本的連結，
        以及 header／main／footer 這副骨架。底下就是那個檔案畫出來的樣子。
        用品牌色標起來的區塊是你要填的 block，其餘由外殼負責，你不去翻它就不會看到。
      




    

      


ui/shell.html 畫出來的樣子
要覆寫哪個 block，就在自己的 base.html 裡寫同名的 block。完整清單在速查表。
      

    
      
  


  


      

        底下四個詞在這一頁有固定的意思，後面每一課都靠它們。
      



    
    

      


這一頁固定用法的四個詞
      

    
      
    

      
markup（標記）
HTML 文字——模板產生、瀏覽器還沒解析的那串東西，例如 <div id="board">…</div>。後面說某條路由「有 markup 在等著」，意思是有一份模板準備把 handler 的回傳值變成 HTML，而不是變成 JSON
    
  
    

      
外殼 shell
指 ui/shell.html，也就是上面那張圖：包在你的頁面外面的那份文件——<head>、header、<main>、footer 與 toaster
    
  
    

      
fragment（片段）
一段不成文件的 HTML：沒有 <!doctype>、沒有 <head>，只有那幾個元素。htmx 的回應裝的就是它
    
  
    

      
partial
渲染出 fragment 的那份模板。檔名以底線開頭，不 extends 外殼，整頁與 htmx 端點共用同一份——第 05 課

htmx

      


htmx 的請求與回應
伺服器用 HTML 回應一次 swap。這中間沒有序列化，也沒有要同步的前端狀態。
      

      
      

        一個元素說明要發哪個請求，以及答案要放在哪裡。伺服器回一段 HTML，
        內容就是它本來會放進整頁的那段標記。htmx 把那段放進指名的元素裡。
      

      

        沒有東西被序列化，前端不重新渲染，狀態也不會同時存在兩個地方。
        按下底下的按鈕會發出真正的請求：
        這一頁載了 htmx，並由瀏覽器裡的一支 mock server 扮演 FastAPI 那一側。
      




    

      


一次來回
前端唯一會變的，只有 hx-target 指名的那棵子樹。

      03
htmx

      


hx-target 與 hx-swap
兩個屬性決定一切：換哪個元素，以及怎麼換。
      

      
      

        hx-target 挑元素，
        hx-swap 決定怎麼處理它。
        htmx 最常見的誤解出在這一對上，所以底下用一塊真的板子試。
        每一種組合都會發出真的請求，換進去的也是真的回應。
      

      

        outerHTML 換掉目標元素本身，所以回應必須包含那層外框。
        innerHTML（預設）換掉它裡面的內容，所以回應不能包含外框。
        搞混這兩個會得到一塊板子裡面又一塊板子。

        input 與 select 在 change 時發。
        hx-trigger 用於其餘情況：
        邊打邊搜、延後載入與輪詢都靠它，不需要寫 JavaScript。

      05
htmx

      


partial：一份檔案，整頁與局部共用
整頁 include 的，就是 htmx 端點回傳的那份 fragment，兩者不會不一致。
      

      
      

        partial 是名字以底線開頭的模板。它不 extends 外殼，自己宣告 import，
        並把自己包在會被換掉的那個元素裡。整頁用
{% include %} 放進它，htmx 端點直接回它。
      

      

        所以 fjkit app 裡沒有「更新那一列」這條程式路徑：
        每一次異動都重新渲染整塊板子的 partial 再換進去。
        板子的樣子只有一份定義，第一次繪製與之後每個請求都用它。
        檔案在 repo 的 examples/fjkit-demo/app/templates/tasks/。
      




    

      


請求
      


        
        

    
      
  
        

        

        





  


      

        上面兩個 handler 指的是同一份檔案，而容易誤會的正是這個檔名。
        _board.html 不是一筆任務。它是整塊板子——新增表單、篩選列、
        統計卡，以及表格裡的每一列，全部包在那個所有控制項都指著的
        <div id="board"> 裡。開頭的底線意思是「這不是一頁」，不是「這很小」。
      

      

        所以在第三列按下 Advance，送出的是一個 POST，換回來的是整塊板子：八列全部重新渲染，
        其中一列現在寫著 Doing。這就是 fjkit 的取捨——多渲染一些其實沒變的 HTML，
        換到的是「板子長什麼樣」只有一份定義。底下是那三個檔案，以及裡面每一個 htmx 屬性。
      



    
      

    

        
        
        
    
        
{# tasks/page.html —— 回應整頁的 GET #}
{% extends "base.html" %}
{% from "ui/layout.html" import page_header %}

{% block content %}
  {{ page_header("Tasks", "這頁上每個控制項都在換 #board。") }}

  {# 第一次繪製。POST /tasks 回的也是這一份檔案。 #}
  {% include "tasks/_board.html" %}
{% endblock %}



extends 外殼、寫一個標題，然後 include partial。關於板子的事，沒有第二份描述。
        
{# tasks/_board.html —— 整塊板子：新增表單、篩選列、統計卡與每一列 #}
{% from "ui/button.html" import button, button_group %}
{% from "ui/table.html" import table %}
{% from "tasks/macros.html" import task_row, TASK_COLUMNS %}

{# 外框寫在檔案裡，因為 hx-swap="outerHTML" 換掉的就是它。 #}
<div id="board">

  {% include "tasks/_new_task.html" %}

  {# 篩選列。每顆按鈕都帶著 query string 重新抓一次整塊板子。 #}
  {% call button_group() %}
    {% for value, label in status_filters %}
      {{ button(label, size="xs",
                hx_get=url_for(request, "tasks_board") ~ ("?status=" ~ value if value else ""),
                hx_target="#board", hx_swap="outerHTML") }}
    {% endfor %}
  {% endcall %}

  {% call table(TASK_COLUMNS, rows=tasks) %}
    {# 重複出現的東西寫成 macro，不是在迴圈裡 include。 #}
    {% for task in tasks %}{{ task_row(request, task, filter_query) }}{% endfor %}
  {% endcall %}

</div>



沒有 extends、沒有 doctype，所以它單獨渲染得起來——htmx 端點才能直接回它。
        
{# tasks/macros.html —— 一列，以及從它送出的 htmx #}
{% macro task_row(request, task, filter_query="") %}
  <tr>
    {{ cell(task.title, tone="strong") }}
    {{ cell(badge(task.status.value | capitalize, variant=task.status_variant)) }}
    {% call row_actions() %}
      {# 推進一筆任務——換回來的是整塊板子。 #}
      {{ button("Advance", variant="ghost", size="xs",
                hx_post=url_for(request, "tasks_advance", task_id=task.id) ~ filter_query,
                hx_target="#board", hx_swap="outerHTML",
                hx_disabled_elt="this") }}
      {{ button("", variant="ghost", size="icon-xs", icon_name="trash",
                aria_label="Delete " ~ task.title,
                hx_delete=url_for(request, "tasks_delete", task_id=task.id) ~ filter_query,
                hx_target="#board", hx_swap="outerHTML",
                hx_confirm="要刪掉這筆任務嗎？") }}
    {% endcall %}
  </tr>
{% endmacro %}



列是一個 macro，htmx 也寫在這裡：每個動作都指著 #board、都用 outerHTML，所以回應永遠是整份 partial。

  



      
    

      


一份檔案為什麼夠用
      

    
      
    

      
它是整塊板子，不是一列
_board.html 渲染的是表單、篩選、統計與全部的列。單獨一筆任務是 macros.html 裡的 task_row()——寫成 macro，因為重複出現的東西是 macro，而 partial 是拿來回應請求的
    
  
    

      
外框寫在檔案裡
partial 的第一行就是 <div id="board">。必須如此，因為每個控制項都寫 hx-swap="outerHTML"：被換掉的就是那層外框，回應得把它帶回來
    
  
    

      
同一份 context，只建一次
兩邊都需要 context 裡一模一樣的名字——tasks、stats、status_filters。router 在 board() 裡建一次，兩個 handler 都回傳它
    
  
    

      
篩選條件會跟著走
每個列上的動作都帶著 filter_query，所以在篩到 Doing 的板子上推進一筆任務，換回來的板子還是篩在 Doing
    
  

  


      
    

      


代價是什麼
      

    
      
    

      
線上多送的位元組
每次都是整塊板子。那是幾 KB 的 HTML 交給瀏覽器解析，換掉的是它本來要算的差異——以及一份要跟著同步的前端模型
    
  
    

      
什麼時候不划算
當板子大到你不想整塊重畫時，答案是切出一份有自己 id 的較小 partial，不是換一個更聰明的前端。第 06 課與第 07 課講的都是這個答案
    
  
    

      
焦點
outerHTML 會連焦點所在的輸入框外層一起換掉。htmx 會依 id 還原焦點，所以要撐過 swap 的輸入框要有穩定的 id
    
  
    

      
很大的板子
這裡用的是 templates.page()。只有在列數由使用者決定時，才改用 templates.stream()
    
  

  




    

      


板子示範——新增、推進、刪除
每個控制項都 target #demo-board，而每個回應都是整塊板子的 partial。
      

處理中…    
      
  
        

        





  


      
    

      


值得先知道的陷阱
      

    
      
    

      
整頁跑回來
從 htmx 路由回傳 page.html，會把一整份文件塞進 div 裡。回 partial
    
  
    

      
4xx 不會換
htmx 預設忽略錯誤回應。shell 把 422（而且只有 422）加了回去，被退回的表單因此能以表單本身回來
    
  
    

      
外框弄丟
outerHTML 需要回應帶著那層外框，否則目標直接消失
    
  
    

      
篩選條件掉了
列上的動作必須帶著目前的篩選，否則換進去的內容會默默把畫面重設
    
  
    

      
swap 被繼承
hx-target 與 hx-swap 會從祖先繼承。卡片用 outerHTML 輪詢自己時，卡片裡的按鈕會繼承那個 swap，把本來只要填內容的元素整個換掉。巢在另一個 htmx 元素裡的觸發器，這兩個屬性都要明寫
    
  

  

      
    

      


伺服器端的幫手
      

    
      
    

      
HX-Request
路由靠這個標頭知道自己正在回應一次局部更新
    
  
    

      
HX-Trigger
回應標頭，在前端觸發一個事件。fragment 裡沒有 toaster，fjkit 就是這樣從一次 swap 裡叫出 toast
    
  
    

      
HX-Redirect
從局部更新的回應裡做整頁轉址
    
  
    

      
hx-swap-oob

      06
htmx

      


一次回應，換掉好幾塊：hx-swap-oob
hx-target 只指得到一個元素。當一個答案要動六塊時，另外五塊自己帶著地址。
      

      
      

        到這裡為止每一次 swap 都只有一個 target。會變的東西都包在同一個元素底下時，一個 target 就夠：
        板子是一個 <div id="board">，上面每一顆按鈕都指著它，每一次回應都是整塊板子。
      

      

        搜尋結果不是單一區塊。一次查詢要動六塊：表格上方的計數、表格本身、側欄的進度卡、
        facet 清單、同負責人面板，以及表格下方的明細面板。它們分散在三個地方，
        唯一同時包住它們的元素是 <body>，而換掉 body 等於重新整理整頁。
      

      

        所以回應把另外五塊走頻外（out of band）送回去，不走
        hx-target 描述的那條唯一通道。每一塊靠自己身上的 id 指出去處。
      




      

        看回應之前，先看觸發的那一端：它一點都不特別，而這正是重點。一個輸入框、一個
        hx-get、一個 hx-target，形狀跟第 03 課一樣。
        它指名 #search-matches，頁面上其他區塊它一個都不知道。
      



    
      

    

        
        
    
        
{# search/page.html —— 讓這一切開始的那一個控制項 #}
{% call form(action=url_for(request, "search_page"), method="get") %}
  {% call field_row("field-and-button") %}
    {{ text_field("q", label="Search tasks", value=query, type="search",
                  hx_get=url_for(request, "search_page"),
                  hx_trigger="input changed delay:250ms, search",
                  hx_target="#search-matches", hx_swap="outerHTML",
                  hx_push_url="true", hx_indicator="#search-busy") }}
    {{ button("Search", variant="primary", type="submit", icon_name="search") }}
  {% endcall %}
{% endcall %}



任何 fjkit macro 上的 hx_* 參數，都會變成它吐出的元素上的 hx-* 屬性。外面那層 form 帶著 action 與 method，所以關掉 JavaScript 這個查詢照樣送得出去。
        
<input class="input" type="search" name="q" id="q"
       hx-get="/search"
       hx-trigger="input changed delay:250ms, search"
       hx-target="#search-matches"
       hx-swap="outerHTML"
       hx-push-url="true"
       hx-indicator="#search-busy">



只有一個 target。htmx 會把回來的東西換進 #search-matches——而它並不知道這次回應等一下要動另外五塊。

  



    

      


一個按鍵拿回來的東西
GET /search?q=cache，由一個 handler 與一個 response model 回答。
      

    
      
        
<div id="search-matches">…</div>                     ← 沒有標記：這塊進 hx-target
<div id="search-stats"    hx-swap-oob="true">…</div>   ← 自己飛去頂端的計數列
<div id="search-progress" hx-swap-oob="true">…</div>   ← 自己飛去側欄
<div id="search-facets"   hx-swap-oob="true">…</div>   ← 自己飛去側欄
<div id="search-related"  hx-swap-oob="true">…</div>   ← 自己飛去側欄
<div id="search-detail"   hx-swap-oob="true">…</div>   ← 自己飛去表格下方




  


      
    

      


htmx 的處理順序
      

    
      
    

      
1 — 抽出
把回應裡每一個帶 hx-swap-oob 的頂層元素抽出來
    
  
    

      
2 — 就位
依 id 找到頁面上同名的元素，各自換掉
    
  
    

      
3 — 最後才是 target
剩下的才照常進 hx-target
    
  

  


      
    

      


四件要知道的事
      

    
      
    

      
值可以怎麼寫
true 是換掉同 id 的元素；innerHTML、beforeend 這些 swap 詞彙在這裡一樣能用
    
  
    

      
它是靜靜失敗的
id 對不上時整塊被丟掉：不報錯，console 也沒有訊息，那一區停在上一次查詢的數字上
    
  
    

      
只認頂層
包在 wrapper 裡的 oob 元素不算 oob，所以回應那支模板是一排平行 include，沒有外框
    
  
    

      
不要標記 target
絕對不要標記 hx-target 指的那一塊：它會一起被抽走，target 換到的是空字串
    
  

  




      

        fjkit 這一側沒有新機制。頁面與回應 {% include %} 同樣六支
        partial，差別只有一個變數：頁面直接渲染它們，回應讓它們帶上 hx-swap-oob。
        每支 partial 自己給那個旗標一個預設值，所以單獨渲染也成立。
      




    

      


同一批 partial，兩種渲染方式
      

    
      
        
{# _results.html —— 一次 htmx 請求拿回去的東西 #}
{% include "search/_matches.html" %}
{% with oob = true %}
  {% include "search/_stats.html" %}
  {% include "search/_progress.html" %}
  {% include "search/_facets.html" %}
  {% include "search/_detail.html" %}
  {% include "search/_related.html" %}
{% endwith %}

{# _stats.html —— 其餘每一塊的開頭都一樣 #}
{% set oob = oob | default(false) %}
<div id="search-stats"{% if oob %} hx-swap-oob="true"{% endif %}>
  …
</div>




  


      

        好處是版面位置由頁面決定，而且只決定一次。把 facet 卡從側欄搬到主欄，
        router、response model 與 swap 都不用改。檔案在 repo 的
        examples/fjkit-demo/app/templates/search/。下一課講同一頁的另一半，
        因為實際畫面兩種都需要。

htmx

      


一個 id，好幾份 fragment：HX-Trigger
第 06 課的反面：觸發者產生一個 id，每一塊區域拿它問的問題都不一樣。
      

      
      

        上一課的前提是一支 handler 能一次回答所有區域：一次查詢、六份 fragment、
        一個裝得下全部的 response model。在同一頁上點開一列不是這個形狀。
        點擊產生的是一個 id，在意它的每一塊面板各自需要不同的查詢：
        那個任務的細節、那個負責人手上的其他任務。要一支 handler 回答全部，
        它必須 import 這一頁上的每一個 service，而且多加第三塊面板就得回頭改它。
      

      

        所以這次的選取只回應它自己那一塊：結果表，其中那一列被標記起來，
        並把 id 放進 HX-Trigger 送出。htmx 把這個標頭轉成一個 DOM 事件，
        在意它的 fragment 各自聽到之後，自己去要自己的資料。這條路由不知道訂閱者的數量，
        也不知道它們存在。多一塊面板就是多一個訂閱者，沒有路由要改。
      




    

      


負責「選取」的那條路由
用 GET，因為選取沒有改動伺服器上的任何東西。結果表就是這顆按鈕的 hx-target，所以回應就地把它換掉。
      

    
      
        
@router.get("/search/select/{task_id}", name="search_select")
@render("search/_matches.html",
        hx_trigger=lambda task_id: {"task-selected": {"task_id": task_id}})
def select_task(service: ServiceDep, task_id: int, q: str = "") -> MatchesResponse:
    """Mark the row, answer with the table, and tell the panels which id."""
    return _matches(service, q, _selected(service, task_id).id)





  


      

        事件宣告在 hx_trigger，它是 @render 的參數而不是 handler 自己寫的標頭，
        這樣會渲染的路由用的是同一套寫法。callable 每次請求解析一次，
        依名字從 handler 自己的參數取值——這裡是 task_id——外加 result，
        也就是 handler 的回傳值。callable 回傳 None 就不發事件，所以一條路由可以只在某些時候廣播。
      

      

        其餘部分是一條普通的 partial 路由：一份樣板、一個 response model，外加一個事件。
        這個模式便宜的原因就在這裡——swap 與廣播是同一趟來回，寫在同一個地方。
      

      

        同一頁的第二個動作是另一半。推進會改變狀態，所以它發出不同的事件，
        在意的是另一組 fragment。
      




    

      


第二個事件，來自一條會改變東西的路由
回應本身就是那次 swap——detail 面板正是這顆按鈕的 hx-target——而標頭是另外四塊聽到的東西。
      

    
      
        
@router.post("/search/advance/{task_id}", name="search_advance")
@render("search/_detail.html",
        hx_trigger=lambda task_id: {"task-changed": {"task_id": task_id}})
def advance_task(service: ServiceDep, task_id: int) -> DetailResponse:
    """Advance the task, answer with the detail panel, and say what changed."""
    if service.advance(task_id) is None:
        raise HTTPException(status_code=404, detail="task not found")
    return DetailResponse(selected=service.get(task_id))





  


      

        兩個事件，每一份 fragment 各自挑它有理由聽的那個。計數面板聽 task-changed、
        不聽 task-selected，因為選取不會改變計數。facet 面板兩個都不聽，
        因為推進一個任務不會換負責人，也不會換優先級。聽哪些廣播由 fragment 自己決定，
        沒有路由知道它存在。

        只有一條規則撐住這整套：一條路由回應的那份 fragment，不可以訂閱這條路由發出的事件。
        它已經被就地換掉，再聽到那個事件就是同一次點擊把它抓第二次；如果那份 fragment 就是自己的
        target，它不會停下來。htmx 不會擋，因為「訂閱者去要自己的 URL」正是那些屬性的意思。
        所以結果表只聽 task-changed，detail 面板只聽 task-selected：
        每一份對其中一個事件是 target、對另一個是訂閱者，不對同一個事件兩者兼具。
      




    

      


訂閱端
在意的區域都寫這些屬性；不在意的一個都不寫。

<div id="search-stats"

     hx-target="this" hx-swap="outerHTML">…</div>




  


      
    

      


要緊的幾個屬性
      

    
      
    

      
誰在聽
from:body——htmx 在發出請求的那個元素上觸發事件，事件再往上冒泡。面板離那個元素很遠，所以在事件必定抵達的地方聽
    
  
    

      
id 怎麼進來
hx-vals="js:…" 是 id 變回查詢參數的唯一地方。從事件讀取它、而不是把選取狀態記在伺服器上，端點才能維持無狀態，兩個分頁才互不干擾
    
  
    

      
還缺什麼
hx-include——補上事件沒帶的值。計數算的是符合的結果，所以除了 id 還需要搜尋框的值。用一個 selector 從頁面上取，不必讓每個事件都帶著它
    
  
    

      
換掉的是誰
hx-target="this"——每個訂閱者替換自己，所以一次回應只有一塊區域，發送端不需要知道這一頁有幾塊區域
    
  

  


      
    

      


四件要知道的事
      

    
      
    

      
送物件
trigger 的值必須是一個 JSON 物件。htmx 把物件原樣交給 event.detail；其他型別（含陣列）會被包成 {value: …}，讀 event.detail.task_id 的監聽者拿不到值
    
  
    

      
它在 swap 之前觸發
HX-Trigger 在 swap 之前觸發。id 走事件這條路的原因就在這裡：存放選取狀態的 hidden input，在訂閱者讀它的當下還是舊值。需要相反的順序時，標頭是 HX-Trigger-After-Swap
    
  
    

      
繼承會滲進來
hx-vals 會被繼承，htmx 沿著 DOM 往上合併它，而且這條路徑不看 hx-disinherit。訂閱者內部的 htmx 元素——那一列的標題，它本身就是開啟這一列的按鈕——必須寫 hx-vals="unset"，那是唯一能中斷這趟走訪的值
    
  
    

      
N 塊面板，N 次請求
N 個訂閱者就是 N 次請求。扇出發生在頁面上而不是收斂在 handler 裡，這是這個做法的代價。查詢成本高時，用 hx-sync 或一層快取換回來
    
  

  




      

        這兩課回答不同的問題，demo 也沒有把它們拆成兩頁。/search 兩個都問：
        一次查詢是伺服器可以完整回答的問題；一次選取是一個 id，三塊區域各自拿它問不同的事。

請求進行中的那段時間
一次 swap 是一趟來回，預設沒有東西擋得住第二次點擊。兩個屬性涵蓋整段等待。
      

      
      

        htmx 在請求期間把 htmx-request 這個 class 掛到某個元素上，結束後移除。
        沒有寫 hx-indicator 時，那個元素是觸發請求的元素本身；寫了就是選擇器指到的元素。
        其餘交給 htmx 自己在啟動時注入的這段樣式：
      




    

      


htmx 注入的規則
兩個選擇器，逗號分開。
      

    
      
        
.htmx-indicator { opacity: 0; visibility: hidden }

.htmx-request .htmx-indicator,
.htmx-request.htmx-indicator { opacity: 1; visibility: visible; transition: opacity 200ms ease-in }




  


      

        第一個選擇器對應 indicator 在被標記元素內部的情況，例如被點的那顆按鈕裡的 spinner。
        第二個對應 indicator 就是被標記元素本身，也就是 fjkit 的做法：
        spinner(indicator=true) 只加上 htmx-indicator。
        所以一個 loading 狀態不需要 CSS、不需要 JavaScript，也不需要額外一趟來回去問伺服器狀態。
      




    

      


兩個屬性，掛在同一張表單上
examples/fjkit-demo/app/templates/jobs/page.html
      

    
      
        
{% call form(action=url_for(request, "jobs_start"), target="#job-list",
             hx_indicator="#job-busy",
             hx_disabled_elt="find button[type=submit]") %}
  {% call field_row("field-and-button") %}
    {{ select_field("kind", label="Background job", options=kind_options) }}
    {% call row(gap=2) %}
      {{ button("Start", variant="primary", type="submit", icon_name="play") }}
      {{ spinner(indicator=true, id="job-busy", label="Starting the job") }}
    {% endcall %}
  {% endcall %}
{% endcall %}




  


      

        hx-disabled-elt 用同一套機制處理另一個問題：請求期間把選擇器指到的元素設成
        disabled，結束後清掉。擋住雙擊把一筆任務推進兩次、或送出兩份相同的表單，
        只需要這一個屬性。選擇器接受 this、find …／closest …
        這類相對寫法，或一般的 CSS 選擇器。
      




      
    

      


它們的行為
      

    
      
    

      
計數的
兩者都是計數，不是開關：htmx 對每個元素記一個請求計數，所以先回來的那一個不會把另一個請求還在用的控制項提早解鎖
    
  
    

      
不會讓畫面跳動
indicator 用 visibility 與 opacity 隱藏，不用 display。它一直佔著位置，所以出現時畫面不會跳動
    
  
    

      
會繼承
兩者都會繼承：hx-indicator 寫在容器上，裡面所有觸發器共用同一個 spinner。this 與 inherit 都是合法的值
    
  
    

      
它會出聲
選擇器沒中時 htmx 會發出警告——The selector "…" returned no matches!——與對不上的 oob id 不同，後者是靜靜失敗
    
  

  


      
    

      


值得先知道的陷阱
      

    
      
    

      
不要放在 target 裡面
把 indicator 放在 target 外面：放在會被換掉的區塊裡，它會在請求進行中連同 id 一起被換走
    
  
    

      
免費的那個版本
完全不寫 hx-indicator 時，class 直接掛在觸發元素上，所以對按鈕寫 .htmx-request 的樣式是最省事的 loading 狀態
    
  
    

      
它記得
htmx 用 data-disabled-by-htmx 標記自己 disable 掉的元素，所以本來就是 disabled 的控制項，結束後仍然是 disabled
    
  
    

      
請求太快
有些 indicator 只閃一下，那是請求快，不是 indicator 壞掉。jobs 頁的工作在回應之後才跑，所以那張卡片需要輪詢
