01

接線：config、mount、templates

其餘你寫的東西都是你的 app，不是你的前端。

一支 fjkit app 只在三個地方碰到 kit。FjkitConfig 收下所有旋鈕。 mount_fjkit() 直接從安裝好的套件裡供應 stylesheet 與 vendored JS， 並且每個 process 建一次 Jinja environment。@render 指名路由要用的模板。

四個檔案點過去看。沒有 package.json，也沒有 watcher 要開著。 repo 裡的 examples/fjkit-demo 就是同樣這四個，放在一支能跑的 app 裡。

htmx 的請求與回應
伺服器用 HTML 回應一次 swap。這中間沒有序列化，也沒有要同步的前端狀態。
      

      
      

        整個想法就是這樣，而且比看起來小。一個元素說明要發哪個請求，以及答案要放在哪裡。
        伺服器回一段 HTML，就是它本來會放進整頁的那段標記。htmx 把那段放進你指名的元素裡。
      

      

        這中間沒有東西被序列化。前端沒有重新渲染。也沒有狀態同時活在兩個地方。
        同一條路由很樂意用 JSON 回應一支腳本，那是第 06 課，是另一道門，
        不是這段交換裡的一個步驟。按下按鈕：底下那個請求是真的。
        這一頁載了 htmx，而瀏覽器裡有一支 mock server 扮演 FastAPI 那一側。

      03
htmx

      


hx-target 與 hx-swap
兩個屬性決定一切：換哪個元素，以及怎麼換。
      

      
      

        hx-target 挑元素。
        hx-swap 說明要拿它怎麼辦。
        htmx 的困惑大多住在這一對上，所以拿底下這塊真的板子試。
        每一種組合都會發出真的請求，換進去的也是真的回應。
      

      

        outerHTML 換掉目標元素本身，所以回應必須包含那層外框。
        innerHTML（預設）換掉它裡面的東西，所以回應不能包。
        把這兩個搞混就是那個經典 bug：你會得到一塊板子裡面又一塊板子。

htmx

      


partial：一份檔案，整頁與局部共用
整頁 include 的，就是 htmx 端點回傳的那份 fragment——所以它們長不歪。
      

      
      

        接下來是 fjkit 那一半。partial 就是名字以底線開頭的模板。它不 extends 外殼，自己宣告 import，
        並且把自己包在「會被換掉的那個元素」裡。整頁用
{% include %} 把它放進去；每個 htmx 端點則是光禿禿地回它。
      

      

        這就是為什麼 fjkit app 裡沒有「更新那一列」這條程式路徑。
        每一次異動都重新渲染整塊板子的 partial 再換進去。
        「板子長什麼樣」只有一份定義，第一次上色用它，之後每個請求也用它。
        真正的檔案在 repo 的 examples/fjkit-demo/app/templates/tasks/。

值得先知道的陷阱
      

    
      
    

      
整頁跑回來
從 htmx 路由回傳 page.html，等於把一整份文件塞進你的 div 裡——回 partial
    
  
    

      
4xx 不會換
htmx 預設忽略錯誤回應；表單錯誤請回 200，並把重繪過的表單一起帶回來
    
  
    

      
外框弄丟
outerHTML 需要回應裡帶著那層外框，否則目標會直接消失
    
  
    

      
篩選條件掉了
列上的動作必須帶著目前的篩選，否則換進去的內容會默默把畫面重設
    
  

  

      
    

      


伺服器端的幫手
      

    
      
    

      
HX-Request
讓路由知道自己正在回應一個局部更新的那個標頭
    
  
    

      
HX-Trigger
回應標頭，會在前端觸發一個事件——toast 就是這樣被叫起來的（fjkit 0.6）
    
  
    

      
HX-Redirect
從局部更新的回應裡做整頁轉址
    
  
    

      
hx-swap-oob
用同一個回應更新第二個元素——一個計數、一個標籤

htmx

      


沒有 HX-Request：同一條路由回 JSON
handler 回傳的是 model，不是標記。要送出什麼，只取決於一個問題：這個呼叫端有沒有在等標記？
      

      
      

        第 02 課說這段交換裡沒有 JSON，就 swap 本身而言是對的。
        但看一眼 handler 真正回傳的東西：是一個 BoardResponse，不是一串 HTML。
        把前者變成後者的是 @render。當呼叫端不是一個在等標記的瀏覽器時，
        就沒有東西可以渲染進去，model 便直接以 JSON 送出。
      

      

        這就是 render_mode="auto"，FjkitConfig 的預設值。決定它的有兩件事，
        兩件都不是 Accept 標頭：這條路由是什麼，以及
        請求上有沒有 HX-Request: true。頁面路由永遠有標記在等，
        因為它存在的理由就是回應一次冷啟導覽，用 JSON 回應只會換來一片空白的瀏覽器視窗。
        片段路由則只有在 htmx 開口時才有。
      




    

      


auto 會回什麼
第一欄由路由決定，第二欄由標頭決定。

        第三列值得再看一次，因為那是真正拿到手的東西：這個 app 裡每一個 htmx 端點，
        本來就已經是一個 JSON 端點。GET /tasks/board 對 htmx 回一塊看板，
        對 curl 回它背後那個 model。沒有第二條路由、沒有 serializer，
        也沒有一份會跟模板走鐘的 DTO。回傳標註是兩者唯一的描述，所以 FastAPI 早就把
        BoardResponse 放進 /docs 了。
      



    
      

    

        
        
        
    
        
@router.get("/tasks", name="tasks_page")
@render("tasks/page.html", partial="tasks/_board.html")
def tasks_page(service: ServiceDep, status: Status | None = None) -> BoardResponse:
    # A page route: it names a page and a partial, so it always has markup
    # waiting. A navigation gets the page; htmx gets the board.
    return _board(service, status)


@router.get("/tasks/board", name="tasks_board")
@render("tasks/_board.html")
def tasks_board(service: ServiceDep, status: Status | None = None) -> BoardResponse:
    # A fragment route: it names only a partial. htmx gets the board, and
    # anyone else gets BoardResponse as JSON — the API, at no extra cost.
    return _board(service, status)



兩條路由共用一份 handler 內容。第一條同時指定了頁面與 partial，所以永遠有標記可以回給導覽；第二條只指定片段——這正是它落在 auto 的 JSON 那一半的原因。

怎麼覆蓋它
      

    
      
    

      
強制 HTML
decorator 上寫 mode="html"——一個絕不能被序列化的片段
    
  
    

      
強制 JSON
mode="json"——一條就只是 API 的路由，對 htmx 也一樣
    
  
    

      
整個 app
FjkitConfig(render_mode="html") 把整個行為關掉
    
  
    

      
請求贏不了設定
寫死 html 或 json 的路由沒有商量餘地——只有 auto 會去讀那個標頭
    
  

  

      
    

      


兩件要知道的事
      

    
      
    

      
快取
凡是形狀取決於該標頭的回應，fjkit 都會補上 Vary: HX-Request
    
  
    

      
為什麼重要
少了它，CDN 會把快取起來的片段送進一次導覽——一個沒有 shell 的頁面，而且哪裡都不會報錯
    
  
    

      
hx-boosted
boost 過的連結是 htmx 在做一次普通導覽：就這個問題而言它算瀏覽器，所以拿到的是整頁，不是 partial
    
  
    

      
命名規則
檔名以 _ 開頭的模板就是片段——test_conventions.py 本來就在管這條慣例

九種 htmx 模式，以及對應的 handler
畫面各有不同；形狀沒有。每一種都是一個 trigger、一個 target 與一份 partial。
      

      
      

        整套屬性詞彙一個螢幕就放得下，
        「元件」那一頁把它印出來了。
        比較花時間學的是它反覆組成的那幾種排列。這裡把它們連同 fjkit 的寫法一起列出來：
        一個分頁是 macro 呼叫，另一個是回應它的 handler。
      

      

        底下每個 handler 都回一份 partial，而且都是普通的 def，
        所以 Starlette 會把它丟進 threadpool。每種模式都連到它出處的 htmx 頁面。上游的
        文件 與
        屬性參考 短到可以整份讀完，而且值得。

它們的共通點
      

    
      
    

      
一份 partial
頁面 include 它，端點回傳它——同一段 fragment 絕不存在兩種渲染

換品牌：品牌 token 與狀態 token
換品牌是一個 CSS 變數。「綠色代表完成」不在那個轉盤上。
      

      
      

        拉拉看色相。你正在編輯 :root 上的 --primary，
        就是一支 app 會寫在自己 stylesheet 裡的那三行，中間沒有任何建置步驟。
        整頁都會動，包括這個側欄與這些 card，因為這一頁本來就蓋在同一組 token 上。
      

      

        盯著狀態標籤：它們不動。狀態顏色刻意沒有接到品牌上，
        因為「綠色代表完成」必須撐過一次改版。

fjkit check：封閉詞彙表
一條沒有人能不小心違反的慣例，比一條寫下來的慣例值錢。
      

      
      

        fjkit check 讀你的模板，然後拒絕兩種東西：顏色字面值，以及元件詞彙表以外的任何 class。
        utility class 即使今天能用也一樣被拒。如果你的 app 靠某個間距 utility 撐著，
        只因為 fjkit 的外殼剛好吐了它，那麼外殼哪天不吐了，你的 app 就會安靜地壞掉。
      

      

        改改看底下的標記。這支檢查器跑的是 fjkit 自己的規則，用的是它真正的 class 清單
        ——…——跟 CI 裡跑的是同一份程式碼，也跟掃這個站模板的是同一份。
      




    

      


app/templates/tasks/_board.html
      


        
        

    
      
  
        




  


      

        被擋下來的 class 是一種情報。它指名了那個還不存在的元件或參數。
        0.1 落地時，改寫前的模板被判了 258 條違規；改寫後是 0。
