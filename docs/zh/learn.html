在寫路由的地方，把介面一起寫完

頁面、表格、表單、導覽、深色模式與 htmx 局部更新——組成方式是 Jinja macro，寫在 handler 所在的同一份程式碼裡，由一個從不打開前端工具鏈的人寫出來。

這一頁就是它在講的那個東西

不是它的截圖。

底下每一個預覽都是真的 macro 輸出，build 時由 fjkit 自己的 Jinja Environment 渲染。 它周圍這一頁也是：側欄、這些 card、表格與分頁列，都是 demo app 呼叫的同一批 macro， 而 fjkit check 在 CI 裡掃這個站的模板。這裡不可能出現套件沒有的元件。

01

接線：config、mount、templates

其餘你寫的東西都是你的 app，不是你的前端。

一支 fjkit app 只在四個地方碰到 kit。FjkitConfig 收下所有旋鈕， mount_ui() 直接從安裝好的套件裡供應 stylesheet 與 vendored JS， Templates.create() 每個 process 建一次 Jinja environment。

四個檔案點過去看。沒有 package.json，也沒有 watcher 要開著——repo 裡的 examples/board 就是同樣這四個，放在一支能跑的 app 裡。

htmx

      


htmx 的請求與回應
伺服器回的是 HTML。沒有 JSON，也沒有要同步的前端狀態。
      

      
      

        整個想法就是這樣，而且比看起來小。一個元素說明要發哪個請求，以及答案要放在哪裡。
        伺服器回一段 HTML——就是它本來會放進整頁的那段標記——htmx 把那段放進你指名的元素裡。
      

      

        沒有東西被序列化成 JSON，前端沒有重新渲染，也沒有狀態同時活在兩個地方。按下按鈕：
        底下那個請求是真的。這一頁載了 htmx，而瀏覽器裡有一支 mock server 扮演
        FastAPI 那一側。
      




    

      


一次來回
前端唯一會變的，只有 hx-target 指名的那棵子樹。
      

    
      
  


  


    

      


試一次
底下這段來回是一個貨真價實的 htmx 請求。
      


        idle
        

    
      
  
        

        





  


      

        那些 HX-* 標頭，就是一條路由用來分辨「這是局部更新」還是「這是整頁載入」的依據。
        其餘部分是一個再普通不過的 POST——兩端都沒有任何前端框架參與。
      











      03
htmx

      


hx-target 與 hx-swap
兩個屬性決定一切：換哪個元素，以及怎麼換。
      

      
      

        hx-target 挑元素。
        hx-swap 說明要拿它怎麼辦。
        htmx 的困惑大多住在這一對上，所以拿底下這塊真的板子試——每一種組合都會發出真的請求，
        換進去的也是真的回應。
      

      

        outerHTML 換掉目標元素本身，所以回應必須包含那層外框。
        innerHTML（預設）換掉它裡面的東西，所以回應不能包。
        把這兩個搞混就是那個經典 bug——你會得到一塊板子裡面又一塊板子。
      




            


  


    

      


那塊板子
      

    
      
        




  


    

      


這組合怎麼寫，以及回來了什麼

hx-trigger：打字、捲動、輪詢
預設值夠用，其餘情況都靠一個屬性。
      

      
      

        多數時候你根本不寫 trigger：button 在 click 時發，form 在 submit 時發，
        input 或 select 在 change 時發。
        hx-trigger 是給其餘情況用的
        ——也是那個讓你不寫一行 JavaScript 就換到「邊打邊搜」、延後載入與輪詢的屬性。
        底下三個都是活的。
      




    

      


keyup changed delay:400ms
changed 會在值沒變時略過請求；delay:400ms 讓每一次按鍵都把倒數重新開始。

      05
htmx

      


partial：一份檔案，整頁與局部共用
整頁 include 的，就是 htmx 端點回傳的那份 fragment——所以它們長不歪。
      

      
      

        接下來是 fjkit 那一半。partial 就是名字以底線開頭的模板：它不 extends 外殼，
        自己宣告 import，並且把自己包在「會被換掉的那個元素」裡。整頁用
{% include %} 把它放進去；每個 htmx 端點則是光禿禿地回它。
      

      

        這就是為什麼 fjkit app 裡沒有「更新那一列」這條程式路徑。每一次異動都重新渲染整塊板子的
        partial 再換進去——一份「板子長什麼樣」的定義，第一次上色用它，之後每個請求也用它。
        真正的檔案在 repo 的 examples/board/app/templates/tasks/。

活的板子——新增、推進、刪除
每個控制項都 target #demo-board，而每個回應都是整塊板子的 partial。
      

處理中…    
      
  
        

        





  


      
    

      


值得先知道的陷阱
      

    
      
    

      
整頁跑回來
從 htmx 路由回傳 page.html，等於把一整份文件塞進你的 div 裡——回 partial
    
  
    

      
4xx 不會換
htmx 預設忽略錯誤回應；表單錯誤請回 200，並把重繪過的表單一起帶回來
    
  
    

      
外框弄丟
outerHTML 需要回應裡帶著那層外框，否則目標會直接消失
    
  
    

      
篩選條件掉了
列上的動作必須帶著目前的篩選，否則換進去的內容會默默把畫面重設
    
  

  

      
    

      


伺服器端的幫手
      

    
      
    

      
HX-Request
讓路由知道自己正在回應一個局部更新的那個標頭
    
  
    

      
HX-Trigger
回應標頭，會在前端觸發一個事件——toast 就是這樣被叫起來的（fjkit 0.6）
    
  
    

      
HX-Redirect
從局部更新的回應裡做整頁轉址
    
  
    

      
hx-swap-oob
用同一個回應更新第二個元素——一個計數、一個標籤
    
  

  











      06
htmx

      


九種 htmx 模式，以及對應的 handler
畫面各有不同；形狀沒有。每一種都是一個 trigger、一個 target 與一份 partial。
      

      
      

        整套屬性詞彙一個螢幕就放得下——
        「元件」那一頁把它印出來了。
        比較花時間學的是它反覆組成的那幾種排列，所以這裡把它們連同 fjkit 的寫法一起列出來：
        一個分頁是 macro 呼叫，另一個是回應它的 handler。
      

      

        底下每個 handler 都回一份 partial，而且都是普通的 def，所以 Starlette 會把它丟進
        threadpool。每種模式都連到它出處的 htmx 頁面；上游的
        文件 與
        屬性參考 短到可以整份讀完，而且值得。

它們的共通點
      

    
      
    

      
一份 partial
頁面 include 它，端點回傳它——同一段 fragment 絕不存在兩種渲染
    
  
    

      
前端沒有狀態
游標、篩選與編輯模式，全都活在 URL 裡，或活在「畫面上是哪一份 partial」裡
    
  
    

      
狀態放在 URL
任何必須撐過重新整理的東西，都是一個整頁 GET 答得出來的 query string
    
  
    

      
退化得下去
把 hx-* 關鍵字拿掉，同一批 macro 吐出的表單與連結照樣能用
    
  

  

      
    

      


刻意還沒做的
      

    
      
    

      
欄位錯誤
每個欄位 macro 都已經收 error=；Pydantic 那趟來回是 0.3
    
  
    

      
toast
HX-Trigger 標頭今天就有；元件是 0.6
    
  
    

      
對話框

排序

換品牌：品牌 token 與狀態 token
換品牌是一個 CSS 變數。「綠色代表完成」不在那個轉盤上。
      

      
      

        拉拉看色相。你正在編輯 :root 上的 --primary——就是一支 app 會寫在
        自己 stylesheet 裡的那三行，中間沒有任何建置步驟。整頁都會動，包括這個側欄與這些 card，
        因為這一頁本來就蓋在同一組 token 上。
      

      

        盯著狀態標籤：它們不動。狀態顏色刻意沒有接到品牌上，因為「綠色代表完成」必須撐過一次改版。

fjkit check：封閉詞彙表
一條沒有人能不小心違反的慣例，比一條寫下來的慣例值錢。
      

      
      

        fjkit check 讀你的模板，然後拒絕兩種東西：顏色字面值，以及元件詞彙表以外的任何 class。
        utility class 即使今天能用也一樣被拒——如果你的 app 靠 gap-4 撐著，
        只因為 fjkit 的外殼剛好吐了它，那麼外殼哪天不吐了，你的 app 就會安靜地壞掉。
      

      

        改改看底下的標記。這支檢查器跑的是 fjkit 自己的規則，用的是它真正的 class 清單——
        …——跟 CI 裡跑的是同一份程式碼，也跟掃這個站模板的是同一份。
      




    

      


app/templates/tasks/_board.html
      


        
        

    
      
  
        




  


      

        被擋下來的 class 是一種情報：它指名了那個還不存在的元件或參數。0.1 落地的時候，
        改寫前的模板拿到 258 個違規；改寫後是 0。
