每個 macro，以及產生它的那行呼叫

每一個 macro，都有實際渲染的預覽與產生它的那行呼叫。 轉動旋鈕，兩件事會一起變：元件本身，以及你要打出這個結果會寫的那行 Jinja。 底下每一個預覽都是 build 時由 fjkit 自己的 Environment 渲染出來的。

01

每個 macro：呼叫與 HTML

沒有任何 macro 收 class 字串，所以沒有任何呼叫端能自己發明一個顏色。

底下每一個參數都是封閉列舉。沒有 class= 這個逃生口，也沒有色相可以傳。 你挑一個 variant，長什麼樣由 token 層決定。多傳給 macro 的東西一律變成 HTML 屬性： hx_post="/tasks" 會渲染成 hx-post="/tasks"。 這就是 htmx 從頭到尾不必出現在任何一個 macro 定義裡的原因。

      05


      


回饋：alert、spinner、skeleton、dialog
四種說「等一下」「好了」和「這件事沒成功」的方式。
      

      
      

        這四個的差別在誰在等、等什麼，挑哪一個也是照這條分。alert 是一件留在頁面上的事實。
        spinner 和 skeleton 都表示「還沒好」，選哪一個取決於你知不知道等一下會出現什麼形狀：
        skeleton 把那個形狀畫出來，spinner 承認你畫不出來。dialog 則是打斷。
      

      

        其中兩個替你做了無障礙的決定。alert(variant="destructive") 會拿到
        role="alert"，那會打斷螢幕閱讀器正在唸的句子；其餘每個 variant 都是
        role="status"，會等到一個停頓。而多行的 skeleton 是一個
        即時區域而不是六個——六根長條是一件事在載入，不是六件。

      06


      


內容：avatar、item_list、code_block、breadcrumb
承載一個人、一則定義、一段程式或一條路徑的那幾個。
      

      
      

        avatar 是值得先讀簽名的那一個。名字同時是 alt 文字和退回時的縮寫，
        所以兩者不可能互相矛盾；而且一旦有圖片承載了名字，縮寫就會退出無障礙樹——否則同一個人會被唸兩次，
        一次是正常的，一次是兩個沒頭沒尾的字母。
      

      

        breadcrumb 收的是 (label, href) 成對的清單，其中 href 為 none 的那一項
        就是當前頁。這是刻意的：這個元件最常見的做錯方式，就是麵包屑最後一項連到你已經在看的這一頁——
        而參數的形狀讓那件事根本寫不出來。

      07


      


顯示與收合：tabs、collapsible、tooltip
三個收合元件，中間沒有一行 fjkit 自己的 JavaScript。
      

      
      

        collapsible 是原生的 <details>：開合狀態、鍵盤操作、disclosure 角色
        全部來自那個元素，Basecoat 用 CSS 替它加動畫。tooltip 完全畫自一個
        data-tooltip 屬性——根本不存在第二個元素。tabs 是 Basecoat 的，外殼已經載好了。
      

      

        tooltip 的機制有一個後果要講白：CSS content() 從來不會進無障礙樹。
        tooltip 是提示，永遠不能是一個控制項唯一的標籤。當 tooltip 是那個控制項身上唯一的文字時，
        請另外給它 aria_label。

浮層：popover、選單、select、drawer、command
一個 id 進去，四個出來——而且對不上時不會出聲。
      

      
      

        ui/overlay.html 裡的每一個都由 Basecoat 自己的 JavaScript 驅動，外殼已經載了它，
        而且它會在 htmx:afterSwap 時重新掃描——所以由 swap 送進來的浮層不需要任何額外處理就能用。
      

      

        它們共同的東西是 id 接線。一個觸發元素和它的面板靠四個相關的 id 互相找到對方，
        錯一個就靜靜地失敗：面板打得開但永遠不會被唸出來，或者根本打不開。這裡每個 macro 都只收一個
        id 再自己推導其餘的。這就是它們是 macro 而不是一段可以複製的標記的全部理由。
      

      

        select_menu 和 combobox 把值放在一個預先填好的隱藏欄位裡——
        上游出貨的是 value="" 再用 JS 寫進去，那會讓任何重繪這個片段的來回弄丟已經選好的值。
        這兩個都不如 select_field：原生的 <select> 一開始就是正確的，
        而且只花一個元素而不是三十個。

剩下的兩個欄位
再兩個欄位，形狀跟其他欄位一模一樣。
      

      
      

        每一支欄位 macro 都收同樣的 name、label、hint、
        error、id，而且 error 是取代 hint 而不是疊在它上面，
        同時把控制項標成 aria-invalid。這兩個也一樣；值得知道的是它們各自針對自己的機制做了什麼。
      

      

        range_field 會替第一次繪製寫好軌道已填滿的那一段。Basecoat 是從一個自訂屬性去畫它，
        而且只在拖曳時才用 JavaScript 更新——沒有這一步，長條會停在上游的預設值，跟旁邊那個數字對不上。

      10


      


icon()：任何 Lucide 名字，直接內嵌
1,767 個名字，沒有 sprite sheet，沒有 icon font，一個請求都不用發。
      

      
      

        icon("plus") 會把 Lucide 的路徑當成 <svg> 內嵌進去。
        它繼承 currentColor，所以放進 primary 按鈕裡的 icon 顏色本來就是對的，
        而且不管多大都不用付一個網路請求。
      

      

        大部分 macro 直接收 icon_name=：button、stat、
        empty_state、brand、sidebar_link。
        所以你很少會自己呼叫這一個。這個站側欄裡的圖示全部是那樣來的。
        底下是其中一小撮，任何 Lucide 名字都可以。
      




    

      


icon(name, size=16)
      

    
      
        




  


            

      

        名字打錯會在渲染時直接丟例外，而不是印出一個空格子——所以錯字是讓那一頁掛掉，
        而不是讓介面上出現一個洞就這樣出貨。
