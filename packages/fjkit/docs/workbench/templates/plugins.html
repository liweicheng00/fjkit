A plugin adds middleware, an exception handler, or a value every template gets — in one object, registered in one place. {% endset %} {{ page_header("Plugins", intro) }} {# ============================================================== 01 #} {% set t01 %}Two contribution points, because the kit has two moments.{% endset %} {% call lesson("why", "01", "What a plugin is", t01) %} {% call prose() %}

A macro covers what a page draws. It does not cover what happens before the handler runs, or what every template should know without a route passing it along. Sessions need both. So do flash messages, locales and feature flags.

A plugin is one object with two optional methods. mount() runs when the app is constructed. extend() runs when the Jinja environment is built. Both are optional — a plugin that only puts a value in every template writes only the second.

{% endcall %} {{ code("config = FjkitConfig( template_dir=APP_DIR / \"templates\", plugins=(auth, flash), ) mount_fjkit(app, config)", label="app/main.py") }} {% call prose() %}

That is the whole registration. mount_fjkit() already reads this config for the static mount and the environment, so a plugin needs no second call and no import order to get right.

The split is visible on purpose. Hiding it would be friendlier right up until someone's mount() silently never ran.

{% endcall %} {% endcall %} {# ============================================================== 02 #} {% set t02 %}Middleware, handlers, routes — attributed to the plugin that added them.{% endset %} {% call lesson("mount", "02", "mount(): the app side", t02) %} {% call prose() %}

AppSetup is a thin pass-through to FastAPI. What it adds is attribution: a misbehaving plugin is named rather than found by elimination.

warn() is for the combinations only the plugin can recognise. An in-memory session store under a production config, say: it works on your laptop and logs users out at random behind four workers, and nothing in the traceback points at the cause.

{% endcall %} {% endcall %} {# ============================================================== 03 #} {% set t03 %}The per-request context is the part that was missing.{% endset %} {% call lesson("extend", "03", "extend(): Jinja, and every render", t03) %} {% call prose() %}

FjkitConfig.globals is resolved once per process. That is right for a version string and useless for the signed-in user. add_context_processor() is the other half: a callable run once per render, with the live request.

{% endcall %} {{ defs("EnvSetup", [ ("add_template_dir(path)", "searched after the app's templates and before the kit's — a plugin may replace a kit macro, never a file the app wrote"), ("add_global(name, value)", "one value for the whole process"), ("add_filter(name, fn)", "a Jinja filter"), ("add_context_processor(fn, provides=[…])", "merged into every template's context, once per render"), ]) }} {{ code("def extend(self, setup: EnvSetup) -> None: setup.add_context_processor( lambda request: {\"session\": getattr(request.state, \"auth\", None)}, provides=[\"session\"], )", label="the auth plugin's whole extend()") }} {% call prose() %}

Two constraints, both deliberate. A processor is synchronous: it runs inside Templates.page(), which a def handler reaches from the threadpool. A plugin needing I/O does it in middleware and leaves the result on request.state — which is exactly what the line above reads.

And provides= is required rather than inferred. Without it, two plugins quietly fighting over user is discoverable only by rendering a page and noticing. With it, the clash is a startup error naming both.

add_template_dir() is how a plugin that ships UI ships it — section 07 is the worked example. One thing goes with it: the Tailwind build scans an explicit list of directories in fjkit.css, so a plugin inside the kit adds its template directory to that list. Miss it and nothing fails — the templates render, every utility class in them is absent from the stylesheet, and the page just looks broken.

The server holds the token.{% endset %} {% call lesson("auth", "05", "The auth plugin", t05, tag="fjkit.auth") %} {% call prose() %}

The first plugin in the box, and the reason the seam exists. The browser is given one opaque, signed, HttpOnly cookie. The access token, the refresh token and your claims stay in a session store on the server.

This is what an htmx app wants. No htmx:configRequest hook attaching a header, no refresh-and-retry glue, no token in the DOM — the browser sends the cookie on every request because that is what browsers do.

{% endcall %} {{ code("auth = AuthPlugin( secret=os.environ[\"FJKIT_SECRET\"], store=RedisStore(redis.from_url(REDIS_URL)), source=MyOIDCSource(), trusted_origins=[\"https://app.example.com\"], ) mount_fjkit(app, FjkitConfig(template_dir=…, plugins=(auth,)))", label="app/main.py") }} {{ defs("Three seams, replaceable independently", [ ("SessionStore", "MemoryStore for development, RedisStore for production, or your own — five async methods"), ("TokenSource", "how credentials become a session: a password check, an OIDC code exchange, an upstream token swap. Routes see none of it. Put Depends(auth.required) on a router and its handlers keep the signatures they had; the session is on request.state.auth, and in every template as session.

Only the middle row cannot be a 401: a plain navigation has no way to act on one, so it would land on a blank page. htmx is the interesting case — it reads HX-Redirect and returns before it looks at the status code, so the status is free to be honest while the browser still moves the whole page. A navigation is recognised by Sec-Fetch-Mode: navigate, or failing that by Accept mentioning text/html; anything else is the caller a route in render_mode="auto" answers in JSON. The 401 carries no WWW-Authenticate: the field is required by RFC 9110, and every registered scheme is wrong here. Basic would make the browser open its own credential dialog, which is the login form this plugin exists to replace.

A redirect is where messages go to die. HX-Trigger names an event for the page to fire, and the page is replaced before the header arrives; a plain navigation has no JavaScript involved at all. The cookie jar is the only thing that crosses.

So a flash is written as a short-lived signed cookie, read back on the request that lands, rendered into the next page, and cleared in the same breath — which is why it appears once and not again on reload. ui/shell.html already carries a toaster region and fills it from flash, so registering the plugin is the entire setup and no template in your app changes.

{% endcall %} {{ code("flash = FlashPlugin(secret=os.environ[\"FJKIT_SECRET\"]) auth = AuthPlugin(secret=…, trusted_origins=…, flash=flash) config = FjkitConfig(template_dir=…, plugins=(flash, auth))", label="app/main.py") }} {% call prose() %}

auth is handed the flash rather than importing it. Neither plugin depends on the other — auth works without one, and a route that just saved something wants flash.add(response, "Saved") with no session in sight. The app is what connects them, which is the same reason there is no dependency resolution in section 04.

The whole of its Jinja side is one processor, and the reason it hands over a small object rather than a list is worth knowing: a page load fires more requests than the page — an htmx poll, a prefetch, a stylesheet — and any of them would consume the message if consumption meant "a request carried the cookie". So the queue is marked read when it is iterated, which only happens where the toasts are actually drawn.

{% endcall %} {{ code("def extend(self, setup: EnvSetup) -> None: setup.add_context_processor(self._read, provides=[\"flash\"]) def _read(self, request: Request) -> dict[str, object]: # A queue, not a list: it marks itself read when something iterates it. return {\"flash\": _Queue(getattr(request.state, \"flash\", ()), request)}", label="fjkit/flash.py") }} {% call prose() %}

Raise one from anywhere — flash.add(response, "Saved", category="success") — and it appears on whatever page the browser lands on next, as a toast, with no route on that page knowing anything about it. That is the test of whether something should be a plugin at all: could a route have passed it instead? Here it could not, because the route that raises the message is not the route that renders it.

Swagger UI's Authorize dialog can only express what an OpenAPI document can describe: an API key, an HTTP scheme, an OAuth2 flow. An app whose sessions are section 05's — a signed HttpOnly cookie over a server-side token — is none of those. And its Try it out could not send one anyway: it runs fetch() in the browser, and that cookie is precisely the one JavaScript may not read.

So both halves move to the server. Signing in is a Python object your app supplies, which for a fjkit.auth app is the same TokenSource your login page already calls. Sending a request is an in-process replay through your own app, carrying the caller's own cookie through the whole middleware stack — so token refresh, revocation and the Origin check are the ones you already wrote, not a second implementation living in a docs page.

{% endcall %} {{ code("docs = ApiDocsPlugin(title=\"Board API\", home_url=\"/\") mount_fjkit(app, FjkitConfig(template_dir=…, plugins=(auth, docs)))", label="app/main.py") }} {% call prose() %}

That is the whole of the wiring. No route to write, no template to render, no static file to serve: the plugin brings its own router, its own templates, and finds the AuthPlugin in the same plugins tuple to wire the sign-in panel to. Pass flow= instead when the app authenticates some other way, and FastAPI(docs_url=None, redoc_url=None) when you want only this one.
