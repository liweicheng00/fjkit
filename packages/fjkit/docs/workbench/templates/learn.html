This is the whole idea, and it is smaller than it looks. An element names the request to make and where to put the answer. The server answers with a piece of HTML — the same markup it would have put in the page — and htmx drops that piece into the element you named.

Nothing is serialised for the swap, nothing is re-rendered on the client, and no state lives in two places. Press the button: the request below is real. htmx is loaded on this page, and a mock server in the browser plays the FastAPI side.

Now the fjkit half. A partial is any template whose name starts with an underscore. It never extends the shell, it declares its own imports, and it wraps itself in the element the swap replaces. The full page {% raw %}{% include %}{% endraw %}s it; every htmx endpoint returns it bare.

That is why a fjkit app has no "update the row" code path. Every mutation re-renders the whole board partial and swaps it. One definition of what a board looks like, used by the first paint and by every request after it. The real files are examples/fjkit-demo/app/templates/tasks/ in the repository.

Those two handlers name the same file, and the name is the part that misleads. _board.html is not one task. It is the entire board — the create form, the filter bar, the stats card and every row in the table, wrapped in the one <div id="board"> that every control on the page targets. So a click on Advance in row three sends one POST, and what comes back is the board with all eight rows re-rendered, one of them now saying Doing. That is the trade fjkit makes: you render more HTML than strictly changed, and in exchange there is exactly one definition of what a board looks like. Every swap so far has had one target, and that is enough while the things that change sit under one element. The board is a single <div id="board">: every control on it points there, and every response is the whole board.

A search result is not one thing. One query moves a row of counters above the table, the table itself, a progress card, a facet list and a siblings panel in the aside, and a detail panel below it — six fragments in three places, and the only element that contains all six is <body>. Swapping the body is a page reload with extra steps.

So the reply carries the other five out of band — outside the one channel hx-target describes. Each of them says where it belongs by carrying the id it is going to.

{% endcall %} {% endcall %} {# ============================================================== 07 #} {% set t07 %}The opposite problem to lesson 06: the trigger produces an id, and each region has a different question to ask with it.{% endset %} {% call lesson("broadcast", "07", "One id, many fragments: HX-Trigger", t07, tag="htmx") %} {% call prose() %}

The last lesson worked because one handler could answer every region at once: one query, six fragments, one response model holding all of them. Opening a row on that same page is a different shape. The click produces an id, and the panels that care about it each need their own query — the detail of that task, the other tasks its owner has. A handler answering all of them would have to import every service on the page, and a third panel would mean editing it.

So the pick answers with its own region — the table, with the row now marked — and sends the id out in HX-Trigger. htmx raises that header as a DOM event, and the fragments that care listen for it and fetch their own data. The route does not know how many of them there are, or that any of them exist. Adding a panel is one more subscriber and no change to any route.

hx_trigger declares the event. It is a parameter of @render rather than a header the handler writes, so it works the same on a route that also renders. A callable is resolved per request from the handler's own parameters by name — task_id here — plus result, what the handler returned. Returning None from it is not an error, so a route can broadcast only sometimes.

Nothing else about that route is special. It is an ordinary partial route — one template, one response model — with an event attached, and that is what makes the pattern cheap: the swap and the broadcast are one round trip, declared in one place.

A second action on the same page shows the other half. Advance changes a status, so it raises a different event, and a different set of fragments cares.

One rule holds this together: the fragment a route answers with must not subscribe to the event that route raises. It is already being replaced in band, so hearing the event fetches it a second time for the same click. On a fragment that is its own target, that never stops. htmx does not catch it, because a subscriber asking for its own URL is what the attribute says to do. So the table hears only task-changed and the detail panel only task-selected: each is a route's target for one event and a subscriber for the other, never both for the same one.
