A fjkit app touches the kit in exactly three places. FjkitConfig holds every knob. mount_fjkit() serves the stylesheet and the vendored JS straight out of the installed package, and builds the Jinja environment once per process. @render names the template a route answers with.

Nothing is serialised for it, and no client-side state is kept in sync.{% endset %} {% call lesson("exchange", "02", "The htmx request and response", t02, tag="htmx") %} {% call prose() %}

This is the whole idea, and it is smaller than it looks. An element says which request to make, and where to put the answer. The server answers with a piece of HTML, the same markup it would have put in the page. htmx drops that piece into the element you named.

Nothing is serialised for the swap. Nothing is re-rendered on the client. No state lives in two places. The same route will happily answer a script in JSON — that is lesson 06 — but that is a second door, not a step in this exchange. Press the button: the request below is real. htmx is loaded on this page, and a mock server in the browser plays the FastAPI side.

Now the fjkit half. A partial is any template whose name starts with an underscore. It never extends the shell, it declares its own imports, and it wraps itself in the element the swap replaces. The full page {% raw %}{% include %}{% endraw %}s it; every htmx endpoint returns it bare.

That is why a fjkit app has no "update the row" code path. Every mutation re-renders the whole board partial and swaps it. One definition of what a board looks like, used by the first paint and by every request after it. The real files are examples/fjkit-demo/app/templates/tasks/ in the repository.

Every swap so far has had one target, and that is enough while the things that change sit under one element. The board is a single <div id="board">: every control on it points there, and every response is the whole board.

A search result is not one thing. One query moves a row of counters above the table, the table itself, a progress card and a facet list in the aside, and a detail panel below it — five fragments in three places, and the only element that contains all five is <body>. Swapping the body is a page reload with extra steps.

So the reply carries the other four out of band — outside the one channel hx-target describes. Each of them says where it belongs by carrying the id it is going to.

Two attributes cover the whole of the wait.{% endset %} {% call lesson("pending", "07", "While the request is in flight", t07, tag="htmx") %} {% call prose() %}

htmx adds the class htmx-request to an element for the length of a request and removes it afterwards. Without hx-indicator that element is the one that fired the request; with it, it is whatever the selector names. Then this stylesheet — htmx's own, injected at startup — does the rest:

{% endcall %} {% set ind_css = ".htmx-indicator { opacity: 0; visibility: hidden } .htmx-request .htmx-indicator, .htmx-request.htmx-indicator { opacity: 1; visibility: visible; transition: opacity 200ms ease-in }" %} {% call stage("The rules htmx injects", "Two selectors, comma separated.", padded=false) %} {{ code_block(ind_css, label="CSS") }} {% endcall %} {% call prose() %}

The first selector covers an indicator inside the marked element — a spinner in the button that was clicked. The second covers an indicator that is the marked element, which is the shape fjkit uses: spinner(indicator=true) adds htmx-indicator and nothing else, so a loading state costs no CSS and no JavaScript of yours, and no round trip to reveal it.

Lesson 02 said the exchange carries no JSON, and of the swap itself that is true. But look at what the handler actually returned: a BoardResponse, not a string of HTML. @render is what turns one into the other. When the caller is not a browser waiting for markup, there is nothing to render into, so the model goes out as JSON.

That is render_mode="auto", the default on FjkitConfig. Two things decide it, and neither of them is an Accept header: what the route is, and whether the request carries HX-Request: true. A page route always has markup waiting, because a cold navigation is the request it exists for, and answering that with JSON would be a blank browser window. A fragment route only has markup waiting when htmx asked for it.
