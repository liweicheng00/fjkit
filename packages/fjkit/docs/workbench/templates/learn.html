This is the whole idea, and it is smaller than it looks. An element says which request to make, and where to put the answer. The server answers with a piece of HTML, the same markup it would have put in the page. htmx drops that piece into the element you named.

Nothing is serialised for the swap. Nothing is re-rendered on the client. No state lives in two places. The same route will happily answer a script in JSON — that is lesson 09 — but that is a second door, not a step in this exchange. Now the fjkit half. A partial is any template whose name starts with an underscore. It never extends the shell, it declares its own imports, and it wraps itself in the element the swap replaces. The full page {% raw %}{% include %}{% endraw %}s it; every htmx endpoint returns it bare.

That is why a fjkit app has no "update the row" code path. Every mutation re-renders the whole board partial and swaps it. One definition of what a board looks like, used by the first paint and by every request after it. The real files are examples/fjkit-demo/app/templates/tasks/ in the repository.

Every swap so far has had one target, and that is enough while the things that change sit under one element. The board is a single <div id="board">: every control on it points there, and every response is the whole board.

A search result is not one thing. One query moves a row of counters above the table, the table itself, a progress card, a facet list and a siblings panel in the aside, and a detail panel below it — six fragments in three places, and the only element that contains all six is <body>. Swapping the body is a page reload with extra steps.

So the reply carries the other five out of band — outside the one channel hx-target describes. Each of them says where it belongs by carrying the id it is going to.

{% endcall %} {% endcall %} {# ============================================================== 07 #} {% set t07 %}The opposite problem to lesson 06: the trigger produces an id, and each region has a different question to ask with it.{% endset %} {% call lesson("broadcast", "07", "One id, many fragments: HX-Trigger", t07, tag="htmx") %} {% call prose() %}

The last lesson worked because one handler could answer every region at once — one query, six fragments, one response model holding all of them. Opening a row on that same page is not that shape. What the click produces is an id, and the panels that care about it each need a different query: the detail of that task, the other tasks its owner has. A handler that answered all of them would have to import every service on the page, and adding a third panel would mean editing it.

So the pick answers with its own region — the table, with the row now marked — and sends the id out in HX-Trigger. htmx raises that header as a DOM event, and the fragments that care listen for it and go and fetch their own data. The route does not know how many of them there are, or that any of them exist. Adding a panel is one more subscriber and no change to any route.

{% endcall %} {% set bcast_route = "@router.get(\"/search/select/{task_id}\", name=\"search_select\") @render(\"search/_matches.html\", hx_trigger=lambda task_id: {\"task-selected\": {\"task_id\": task_id}}) def select_task(service: ServiceDep, task_id: int, q: str = \"\") -> MatchesResponse: \"\"\"Mark the row, answer with the table, and tell the panels which id.\"\"\" return _matches(service, q, _selected(service, task_id).id)" %} {% call stage("The route that picks", "A GET, because picking changes nothing on the server. The table is the button's hx-target, so the reply swaps it in band.", padded=false) %} {{ code(bcast_route, label="router.py") }} {% endcall %} {% call prose() %}

hx_trigger is where the event is declared, and it is a parameter of @render rather than a header the handler writes, for one reason: then it works the same on a route that does render. A callable is resolved per request out of the handler's own parameters by name — task_id here — plus result, what the handler returned. Returning None from it raises nothing, so a route can broadcast only sometimes.

Nothing about that route is special otherwise. It is an ordinary partial route — one template, one response model — with an event attached, which is what makes the pattern cheap: the swap and the broadcast are one round trip, declared in one place.

A second action on the same page shows the other half of it. Advance changes a status, so it raises a different event, and a different set of fragments cares.

{% endcall %} {% set bcast_shared = "@router.post(\"/search/advance/{task_id}\", name=\"search_advance\") @render(\"search/_detail.html\", hx_trigger=lambda task_id: {\"task-changed\": {\"task_id\": task_id}}) def advance_task(service: ServiceDep, task_id: int) -> DetailResponse: \"\"\"Advance the task, answer with the detail panel, and say what changed.\"\"\" if service.advance(task_id) is None: raise HTTPException(status_code=404, detail=\"task not found\") return DetailResponse(selected=service.get(task_id))" %} {% call stage("A second event, from a route that changes something", "The reply is the swap — the detail panel is this button's hx-target — and the header is what the other four hear.", padded=false) %} {{ code(bcast_shared, label="router.py") }} {% endcall %} {% call prose() %}

Two events, and each fragment picks the ones it has a reason to hear. The counters listen for task-changed and not task-selected, because picking a task changes no count. The facets listen for neither, because advancing one changes no owner and no priority. Which broadcasts a fragment hears is the fragment's own decision, and no route knows it exists.

One rule holds this together: the fragment a route answers with must not subscribe to the event that route raises. It is already being replaced in band, so hearing the event too fetches it a second time for the same click — and on a fragment that is its own target, it never stops. htmx will not save you, because a subscriber asking for its own URL is exactly what the attribute says to do. That is why the table hears only task-changed and the detail panel only task-selected: each is a route's target for one event and a subscriber for the other, never both for the same one.

htmx adds the class htmx-request to an element for the length of a request and removes it afterwards. Without hx-indicator that element is the one that fired the request; with it, it is whatever the selector names. Then this stylesheet — htmx's own, injected at startup — does the rest:

{% endcall %} {% set ind_css = ".htmx-indicator { opacity: 0; visibility: hidden } .htmx-request .htmx-indicator, .htmx-request.htmx-indicator { opacity: 1; visibility: visible; transition: opacity 200ms ease-in }" %} {% call stage("The rules htmx injects", "Two selectors, comma separated.", padded=false) %} {{ code_block(ind_css, label="CSS") }} {% endcall %} {% call prose() %}

The first selector covers an indicator inside the marked element — a spinner in the button that was clicked. The second covers an indicator that is the marked element, which is the shape fjkit uses: spinner(indicator=true) adds htmx-indicator and nothing else, so a loading state costs no CSS and no JavaScript of yours, and no round trip to reveal it.

hx-disabled-elt is the same machinery aimed at a different problem. Lesson 02 said the exchange carries no JSON, and of the swap itself that is true. But look at what the handler actually returned: a BoardResponse, not a string of HTML. @render is what turns one into the other. When the caller is not a browser waiting for markup, there is nothing to render into, so the model goes out as JSON.

That is render_mode="auto", the default on FjkitConfig. Two things decide it, and neither of them is an Accept header: what the route is, and whether the request carries HX-Request: true. A page route always has markup waiting, because a cold navigation is the request it exists for, and answering that with JSON would be a blank browser window. A fragment route only has markup waiting when htmx asked for it.
