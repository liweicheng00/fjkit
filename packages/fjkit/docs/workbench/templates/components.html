Every parameter on this page is a closed enumeration. There is no class= escape hatch and no hue to pass: you pick a variant, and the token layer decides what it looks like. Anything a macro does not name becomes an HTML attribute, so hx_post="/tasks" renders as hx-post="/tasks". That conversion is one file, ui/attrs.html, which every macro forwards its leftover keywords to and no app ever calls. It is why htmx appears in no macro definition in the kit, and why a keyword a macro has never heard of is an attribute rather than an error.

button is the macro every other file reaches for, and the one whose signature is worth learning first: variant and size are closed lookups, href switches the element to an <a> and drops type, and icon_name takes any Lucide name so a caller never imports icon to put a glyph on a button.

button_group is two components under one name, and the knob tells you which: horizontal is a row, so the gap is yours; vertical is Basecoat's .button-group, which joins the buttons into a single control with shared borders and has no gap to give.

Everything in ui/overlay.html is driven by Basecoat's own JavaScript, which the shell already loads and which re-scans on htmx:afterSwap, so an overlay that arrives in a swap works with nothing extra.

What they share is id wiring. A trigger and its panel find each other through four related ids, and getting one wrong fails silently: the panel opens but is never announced, or never opens at all. Every macro here takes one id and derives the rest, which is why they are macros rather than markup to copy.

select_menu and combobox put their value in a hidden input, pre-filled. Upstream ships value="" and writes it from JS, which loses the selection on any round trip that re-renders the fragment. Prefer select_field to either: a native <select> is correct for free and costs one element instead of thirty.

Both take multiple=true, and both then want a list in selected where they took a scalar before. The hidden input carries Basecoat's JSON array, and multiselect_scripts() — one script, opted into by the page that has such a field — re-emits it on submit as the repeated field HTML has always used: labels=bug&labels=ui. The route stays ordinary at labels: list[str] = Form([]), with no parsing anywhere. Forget the script and the field posts one JSON-shaped string instead, which is a 422 on a page that looks correctly filled in.

A checkbox group inside a fieldset posts the same thing and needs no script at all. It is the better answer up to about a dozen options, which is where these two start.

columns is a list of dicts — label, and optionally align, width, sort, sort_url or select — and the macro tests rows to decide whether to render your body or the empty state. That is why it takes rows it does not iterate: no caller repeats the if-rows-else branch, and no page can ship a table that renders as a lone header row.

A repeated row is a macro call inside your loop. {% raw %}{% include %}{% endraw %} there is a template lookup plus a fresh context per iteration, which is the difference the benchmark on the Learn page measures.

A column carrying a sort_url becomes a sortable header, and pagination goes under the table. Neither builds a URL: the router owns the query string, because it is the only thing that knows which filters are on. Both render real hrefs and take target= to add the htmx swap on top — an order and a page number are the two things about a list that people bookmark, so both have to survive JavaScript being off.

{% raw %}{"select": true}{% endraw %} puts a batch-selection column in front of the rest. It posts as the repeated field a checkbox column has always sent, and select_scripts() is what ticks the whole column from the header box.

page_size is a <form method="get">, and that is the design rather than an implementation detail: a <select> on its own has no way to act when its value changes, and the kit does not script one. Its url must carry no query string, because a native GET submit replaces the whole query with the form's own fields — so the filters travel in keep as hidden fields. The page number never does. It names a position, and changing the size moves every position.

Basecoat owns which tab is selected, the roving tabindex and the arrow keys, and the shell already loads it. This macro carries the aria contract that behaviour reads: a [role="tab"] whose aria-controls names a [role="tabpanel"] with that id. Getting that pairing right by hand is what a component should stop you having to think about.

selected names the tab that starts open. The server knows which one the request was for, so it is a parameter rather than something a script decides after paint. The two representations under every playground on this page are one of these.
