macro 管的是一頁畫出什麼。它管不到 handler 執行之前發生的事，也管不到「每個模板都該知道、 但不該由每條路由傳過去」的東西。session 兩者都要；語系與 feature flag 只要後者； flash 訊息只要前者。

轉址是訊息的墳場。HX-Trigger 是叫頁面去觸發一個事件，但頁面在那個標頭抵達之前 就被換掉了；一般導覽更是從頭到尾沒有 JavaScript 參與。唯一跨得過去的只有 cookie。

所以 flash 是一個短命的簽名 cookie：在轉址的那個回應上種下去，在落地的那個請求上讀回來， 跟其他訊息一樣排進 fjkit.messages，並在真的被顯示過之後才清掉——這就是它只出現 一次、重新整理不會再跳的原因。ui/shell.html 裡的 toaster 區域本來就在，也本來就 在畫那個佇列，所以註冊 plugin 就是全部的設定，你的模板一個字都不用改。

auth 是被交給 flash，而不是自己 import 它。兩個 plugin 誰也不依賴誰——auth 沒有 flash 也能跑，而一條剛存好資料的路由想要的是 flash.add(response, "Saved")，跟 session 毫無關係。把它們接起來的是 app， 這也是第 04 節裡沒有相依解析的同一個理由。

它在 Jinja 那一側什麼都沒有——沒有 extend()，也沒有任何屬於自己的 context key。 cookie 是在 middleware 裡排進 fjkit.messages 的，所以模板永遠不會知道這則訊息 是搭 cookie 來的、而不是它正在渲染的那個 handler 給的。這就是第 06 節那個分層換來的東西： shell 裡一個迴圈，而不是每種送達方式各一個。

有意思的是那顆 cookie 什麼時候被清掉，答案是「等到 messages.shown(request) 為真」——也就是等到有模板迭代過那個佇列，或佇列被序列化進 HX-Trigger。一次頁面 載入發出的請求不只頁面本身——htmx 的輪詢、prefetch 都算——如果「顯示過」的定義是「這個請求 帶了那顆 cookie」，其中任何一個都會把訊息吃掉，讓它本來該出現的那一頁空著。
