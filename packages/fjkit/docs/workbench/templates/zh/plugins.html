macro 管的是一頁畫出什麼。它管不到 handler 執行之前發生的事，也管不到「每個模板都該知道、 但不該由每條路由傳過去」的東西。session 兩者都要，flash、語系、feature flag 也是。

plugin 是一個物件，兩個方法都可選。mount() 在 app 建構時執行， extend() 在 Jinja environment 建立時執行。只想給每個模板一個值的 plugin， 就只寫後面那個。

註冊就這樣而已。mount_fjkit() 本來就要讀這份 config 來掛靜態檔與建 environment，所以 plugin 不需要第二個呼叫，也沒有 import 順序要記。

轉址是訊息的墳場。HX-Trigger 是叫頁面去觸發一個事件，但頁面在那個標頭抵達之前 就被換掉了；一般導覽更是從頭到尾沒有 JavaScript 參與。唯一跨得過去的只有 cookie。

所以 flash 是一個短命的簽名 cookie：在轉址的那個回應上種下去，在落地的那個請求上讀回來， 渲染進下一頁，並在同一個回應裡清掉——這就是它只出現一次、重新整理不會再跳的原因。 ui/shell.html 已經帶了 toaster 區域並從 flash 填它，所以註冊 plugin 就是全部的設定，你的模板一個字都不用改。

{% endcall %} {{ code("flash = FlashPlugin(secret=os.environ[\"FJKIT_SECRET\"]) auth = AuthPlugin(secret=…, trusted_origins=…, flash=flash) config = FjkitConfig(template_dir=…, plugins=(flash, auth))", label="app/main.py") }} {% call prose() %}

auth 是被交給 flash，而不是自己 import 它。兩個 plugin 誰也不依賴誰——auth 沒有 flash 也能跑，而一條剛存好資料的路由想要的是 flash.add(response, "Saved")，跟 session 毫無關係。把它們接起來的是 app， 這也是第 04 節裡沒有相依解析的同一個理由。

它在 Jinja 這一側只有一個 processor，而它交出去的是一個小物件而不是一個 list，理由值得 知道：一次頁面載入發出的請求不只頁面本身——htmx 的輪詢、prefetch、樣式表都算——如果「消耗」 的定義是「這個請求帶了那個 cookie」，其中任何一個都會把訊息吃掉。所以那個佇列是在被 迭代時才標記為已讀，而那只發生在真正畫出 toast 的地方。

{% endcall %} {{ code("def extend(self, setup: EnvSetup) -> None: setup.add_context_processor(self._read, provides=[\"flash\"]) def _read(self, request: Request) -> dict[str, object]: # 是佇列不是 list：有東西迭代它的時候，它會把自己標記成已讀。 return {\"flash\": _Queue(getattr(request.state, \"flash\", ()), request)}", label="fjkit/flash.py") }} {% call prose() %}

在任何地方發一則——flash.add(response, "Saved", category="success")——它就會 出現在瀏覽器接下來落地的那一頁上，長成一個 toast，而那一頁的路由對它一無所知。這也是判斷 一樣東西該不該做成 plugin 的標準：這個值，路由自己傳得過去嗎？這裡傳不過去，因為發出訊息 的那條路由，不是渲染它的那條。
