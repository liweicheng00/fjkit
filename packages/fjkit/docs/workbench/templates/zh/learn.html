{{ link("hx-target", "https://htmx.org/attributes/hx-target/") }} 挑元素， {{ link("hx-swap", "https://htmx.org/attributes/hx-swap/") }} 決定怎麼處理它。 htmx 最常見的誤解出在這一對上，所以底下用一塊真的板子試。 每一種組合都會發出真的請求，換進去的也是真的回應。

outerHTML 換掉目標元素本身，所以回應必須包含那層外框。 innerHTML（預設）換掉它裡面的內容，所以回應不能包含外框。 搞混這兩個會得到一塊板子裡面又一塊板子。

到這裡為止每一次 swap 都只有一個 target。會變的東西都包在同一個元素底下時，一個 target 就夠： 板子是一個 <div id="board">，上面每一顆按鈕都指著它，每一次回應都是整塊板子。

搜尋結果不是單一區塊。一次查詢要動六塊：表格上方的計數、表格本身、側欄的進度卡、 facet 清單、同負責人面板，以及表格下方的明細面板。它們分散在三個地方， 唯一同時包住它們的元素是 <body>，而換掉 body 等於重新整理整頁。

所以回應把另外五塊走頻外（out of band）送回去，不走 hx-target 描述的那條唯一通道。每一塊靠自己身上的 id 指出去處。

上一課的前提是一支 handler 能一次回答所有區域：一次查詢、六份 fragment、 一個裝得下全部的 response model。在同一頁上點開一列不是這個形狀。 點擊產生的是一個 id，在意它的每一塊面板各自需要不同的查詢： 那個任務的細節、那個負責人手上的其他任務。要一支 handler 回答全部， 它必須 import 這一頁上的每一個 service，而且多加第三塊面板就得回頭改它。

第三層也不是第二層的超集合。轉址會換掉整頁，本來要顯示訊息的那份文件在回應抵達前 就不存在了，唯一跨得過去的只有 cookie。但對不是轉址的回應來說，同一顆 cookie 是 錯的工具：一則馬上就要渲染出來的訊息不必多跑一趟。所以兩者是疊起來而不是合而為一： FlashPlugin 把 cookie 排進 fjkit.messages，shell 裡因此只有一個 迴圈，而不是每種送達方式各一個。

FastAPI 對一份被退回的表單回的是 {"detail":[{"type":"missing",…}]} 加一個 422。 對 API 來說這正確，對一頁畫面來說等於什麼都沒有：htmx 預設不會 swap 4xx， 所以正在填表單的人看到的是按了沒反應，而一般的 POST 會把他丟到一整頁 JSON 上。

解法是利用那個回應原本就有的內容。它點名每個失敗的欄位，用的正是表單送出時的名字， 訊息也是給人讀的；而表單還在頁面上，使用者打過的每一個字都還在控制項裡。 沒有東西需要重新渲染、記住或重建。

所以 mount_fjkit() 把 422 原封不動送回去，由 shell 載入的一支 script js/errors.js 把每則訊息寫到它的欄位下面。每個 handler 的簽名還是 FastAPI 寫的那個， 也沒有任何一條路由要替「被退回」這個狀態指名模板，因為沒有東西要渲染。
