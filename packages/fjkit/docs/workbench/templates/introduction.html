Every component you will see is rendered by fjkit's own Jinja environment, and the page around it — this card, the sidebar, the tables — is built from the same macros. fjkit check runs over these templates in CI, so the site cannot show you a component the package does not ship, or a class an app is not allowed to write.

{% endcall %} {% endcall %} {# ============================================================== 01 #} {% set i01 %}A screen is a route, a template, and a handful of macro calls.{% endset %} {% call lesson("what", "01", "What fjkit is", i01) %} {% call prose() %}

fjkit is the layer between your FastAPI handlers and the browser. You wire it once, and then every screen is a template that calls macros: page_header, card, table, form, sidebar. There is no second application to build, no second language, and no second place to look when something breaks.

The constraint that shapes everything else: Tailwind runs when fjkit is released, not when your app runs. Your repository has no package.json, no node_modules, no Tailwind binary, and nothing to rebuild after you edit a template. Both files below are read straight off the demo app in this repository.

The reasoning behind each is in CHARTER.md §2 in the repository, and the Learn page demonstrates four of them in the browser — including the brand knob, which repaints the page while you watch.

The last one is the one people do not expect, so it is worth saying plainly. A fjkit handler returns a model, not markup; @render decides the wire format from whether the caller has markup waiting. So GET /tasks/board answers htmx with a rendered board and answers curl with BoardResponse as JSON — same route, same handler, same return annotation, and FastAPI has already documented it in /docs. Both halves of that reply are on the Learn page.
