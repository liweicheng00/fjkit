Basecoat already ships `.tabs` and its behaviour: its vendored script owns the selection, the `hidden` on the other panels, and the ArrowLeft/Right/Home/End keys. The style pack does ship one, a pill strip; fjkit draws underline tabs, so `fjkit.css` turns the pack's geometry off before painting its own. {%- endmacro %} {# tab_panel(id, lazy, on, include) — the body for one tab. The id is the one the tab's `aria-controls` named; Basecoat hides and reveals it from there. No `hidden` is rendered here: Basecoat's script sets it on init, and a panel that arrived pre-hidden would be invisible to a reader with JavaScript off. This way the panels stack and every one is legible. `lazy` is a URL, and it is all a panel needs to fetch its own body when it is shown rather than when the page loads. Without `lazy` the panel is inert markup, and `on` and `include` are read only alongside it because neither means anything on its own. The block's body means two things, depending on the panel: * **The open panel** — the one `tabs(selected=…)` names — holds its real content, rendered by the page route: the same partial `lazy` returns. It does not fetch at load. The server already knows which tab the request was for, and a panel that fetched what the page had just rendered would cost a request per page view and, with `hx_push_url`, a duplicate history entry that makes Back land on the same URL. * **Every other panel** holds a stand-in, usually a `skeleton`, shown until its first fetch arrives. Exactly two things make a lazy panel fetch: * **Its tab going from hidden to shown**, by a click or by the arrow, Home and End keys Basecoat handles. The open panel's first showing is the page load, which does not fetch; every later showing does, the open one included. Re-clicking the selected tab, a click or a key inside the panel, and scrolling the page do not. * **Each event in `on`**, while the panel is shown. Five decisions are baked in here so that no app template has to remember them. Each is a way this goes silently wrong when written by hand: * The tab switch, not the viewport. `revealed` tests visibility with `getBoundingClientRect`, and an element hidden by `display:none` — which is what the `hidden` Basecoat sets means — reports an all-zero rect. `top < innerHeight` and `bottom >= 0` both hold for that rect, so every panel on the page counts as revealed and fetches at load. `intersect` gets the hidden panel right, but an `IntersectionObserver` reports entering the viewport, and a panel enters it on every scroll back as well as on a tab switch: a tall panel above a long table reloaded itself each time the reader came back up (0.4.3). * `click` and `keydown` from the `.tabs` container. Basecoat's listeners are on the tablist, and its arrow keys call `select()` without a click, so the tab a key lands on hears no event of its own. The container is an ancestor of the tablist: both events reach it after Basecoat has moved `hidden`, whichever tab they started on. A nested group's events bubble to the outer container too, and change nothing there. * A filter that fetches on a change, not on an event. Every click and key in the group reaches every panel, so each panel keeps what it last was in `data-fjkit-shown` and lets the request through only when it went from hidden to shown. Before the first event the panel has no mark, and its starting state is read from its tab: shown if the tab carries `data-fjkit-open`. The mark is on the panel and the test is on the tab because Basecoat moves `aria-selected` and `hidden` as the user clicks, and neither says what the server rendered. The filter ends in a comparison and a negation, so it returns a boolean: htmx runs the request only when a filter returns exactly `true`. * A filter on every broadcast. The events in `on` are raised on ``, and a hidden panel hears them as well as the open one does. Four tabs would mean four requests per broadcast, three of them for markup nobody is looking at. `[!this.hidden]` is the whole fix, and it is this short only because the trigger sits on the panel — the element carrying the `hidden` — rather than on something inside it. * `innerHTML` onto the panel. The panel carries the trigger and the mark its filter keeps; a reply that replaced it would bring a panel that remembers nothing and reads its starting state from the tab again. A switch made by calling Basecoat's `select()` from a script raises no click or key, and does not fetch. Nothing in fjkit calls it. `hx_push_url="true"` passes through and is supported: each tab becomes a URL. Back and Forward then reload the page at that URL rather than restore an htmx snapshot — `ui/shell.html` turns the snapshot cache off for every page, and says why. `include` is a selector for what the panel has to send: the id it is about, the query it is filtered by. A selector rather than a value carried in the event, because the two paths into this panel disagree on what an event is — a tab switch carries no id. A panel hidden when the pick happened never heard `task-selected` and has only the page to read, so the id has to be on the page and the route that changes it has to say so **after** its own swap: `@render(..., hx_trigger_after_swap=...)`. See `fjkit.rendering.render`. A lazy panel refetches on every tab switch to it, not only the first.
